Your tokenizer is the bottleneck, and that's the point

Here's a number that should not be true: a tokenizer that runs 1000x faster than the standard one. Not by being clever about attention, not by shrinking the model, but by doing something so obvious in retrospect that the only real mystery is why it took us this long.

Which means the transformer was never the thing slowing you down. It just looked that way, because it's the part with the paper and the math and the terrifying FLOP count. And sitting right in front of it, like a toll booth on the only road into town, is a function that takes a string of text and chops it into pieces. That function is tokenization, and it has been running the same way since before any of us heard the word "transformer."

The toll booth at the edge of town

Most tokenizers are glorified regex engines. They scan the input character by character, building up a vocabulary of subword units, and they do it all in a single-threaded, instruction-by-instruction slog that would make a 1980s spreadsheet blush. It's a sequential dependency, a single point of failure where the entire request queues up before the "intelligence" even gets a chance to start.

This isn't a minor inefficiency. It's a structural bottleneck, and it's been hiding in plain sight since the very first transformer paper. You've built a high-speed rail line for the model, and then you make every passenger walk through a single turnstile that can only process one ticket at a time.

The 1000x speedup and what it proves

So when a new tokenizer comes along and claims a 1000x speedup, the reaction shouldn't be "wow, that's fast." It should be "holy hell, how bad were we letting it get?" The problem wasn't that tokenization is hard. The problem was that we assumed it had to be slow, so we never looked at it.

The fix is almost embarrassingly simple. You load the entire input string into a register, and you let the hardware chew through sixteen characters at a time with a single instruction. The ship doesn't go faster, but it carries a lot more per trip.

This is exactly the argument that Mitchell Hashimoto makes in his post about why everyone should know SIMD: that the biggest wins in systems programming are often not in the clever algorithms, but in the boring, mechanical act of using the hardware the way it was designed to be used. The tokenizer wasn't slow because it was doing something hard. It was slow because it was doing something easy, one character at a time, on a machine that can do sixteen at once. They just finally started using the hardware that was already sitting there.

You've built this machine

Now here's the part that should make you uncomfortable. It's not that the tokenizer is slow. It's that every production LLM pipeline already has this same bottleneck hiding somewhere.

You have built this machine. Probably several times.

Every time you serialize an object to JSON, you're running a sequential parser. Every time you parse a log line with a regex, you're running a state machine that could be a lookup table. Every time you process a string with a loop, you're leaving performance on the table that a vectorized instruction could have picked up.

The first thing is to stop trusting your intuition about where the time goes. Not the happy-path benchmarks, but the production traces with real user inputs and real latency targets. The profiler is the only honest broker in the performance game, and it will tell you exactly which of your assumptions are structural and which are just habits.

The second thing is broader. When you see a claim like "1000x faster tokenizer," don't just file it under "cool, someone else's problem." Ask yourself what else you're doing the slow way out of habit. What's the regex that you've always used because it's easy and never felt slow enough to justify the fuss?

The march of progress doesn't come from making the big, obvious thing 10% faster. It comes from finding the toll booth you didn't know you had, and realizing the road was always wide enough to let everyone through at once. And that's a much more hopeful place to start, because it means the next 1000x is out there, waiting for you to profile your own turnstile.
