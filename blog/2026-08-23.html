Your local model isn't dumber. Your defaults are.

The same file. Byte-identical weights, same checksum, sitting on disk. Load it in one runtime and it reasons its way through a long tool-calling task; load it in another and it starts talking to itself, loops inside its own thinking block, and never comes out. Nothing about the model changed. What changed was a chat template, a temperature someone picked because it looked sensible, and a context window that quietly threw away the middle of your prompt.

That's the whole story, and it's worse than it sounds.

You should care because you are almost certainly making decisions on bad evidence right now. Somebody on a forum said the model was incredible, you pulled a quant, poked it with three prompts at temperature zero, and concluded it was overhyped. You didn't evaluate a model. You evaluated an accidental configuration that nobody wrote down, including you.

Start with what actually happens when a token comes out. The model produces logits — a raw score for every token in its vocabulary, tens or hundreds of thousands of numbers, one per candidate. Those get normalized into a probability distribution. Then the sampler — temperature, top-p, whatever you've configured — draws one. The detokenizer turns it back into text, the whole sequence goes back in, and it happens again. One draw at a time, each draw conditioned on every draw before it, which means every small distortion compounds forward instead of averaging out.

Now notice where the fragility lives. It is not in the weights. It is in every single step around them.

The sampler is the loudest offender because it's the one you're allowed to touch. Model cards on Hugging Face usually specify exactly what to use — temperature 1.0, top-p 0.95, whatever that particular lab tuned against — and it varies by model, which nobody expects and everybody ignores. Set the temperature too low on a reasoning-tuned model and you get the pathology people complain about constantly: it sits there looping, unable to escape its own thinking output. That is not the model being stupid. You flattened the distribution until the single highest-probability continuation of "thinking" was more thinking, forever, and you removed exactly the noise that would have let it jump the rail.

Then the chat template, which is worse, because it's invisible. The template is the scaffolding that turns your messages into the precise token sequence the model was trained to expect: special tokens, role markers, newlines in specific places. During training the model learned that one particular byte pattern means "the user has stopped talking and it is now your turn." Get a single newline wrong and you have handed it a sequence that appeared nowhere in training. It will still answer. It always answers. It just answers from slightly off-distribution — a little less coherent, a little more willing to ignore your system prompt — and no error is raised anywhere, because from the runtime's point of view nothing went wrong.

The chat template is a key, and the model is a lock with a hundred million tumblers. A key that's off by a fraction still slides into the slot. It still turns, partway. The door even opens a crack, enough to convince you the lock is cheap junk. Where the analogy breaks is the useful part: a real lock either opens or it doesn't, while the model degrades smoothly and silently across a continuum, which is precisely why nobody catches it.

Then context truncation, sneakiest of the lot. Long prompt, runtime silently discards whatever doesn't fit, and now the model is answering a question you did not ask. Add quantization, which doesn't merely make weights smaller — it reshapes the output distribution, blunting exactly the low-probability tail that a sampler needs to escape a loop. Add the hardware: mixed GPU generations with different instruction sets executing the same matrix math in different orders, accumulating floating-point error differently, producing genuinely different next-token probabilities from identical weights. That last one is not a bug you can fix. It's just true.

There is a way to measure the drift, and it's worth knowing the name: KL divergence. Take the output distribution from your setup, take a baseline distribution, measure how far one has moved from the other. Lower KLD means closer to the baseline — not automatically better. It's directional, so which distribution you put first changes the number. And it is uninterpretable unless the author discloses the reference checkpoint and the full runtime environment. An impossibly low KLD on a quant's model card, with no disclosure, is a marketing number wearing a lab coat.

Which is when the assumption you've been resting on quietly collapses. You have been treating the hosted API as the honest baseline — the real model, the one the benchmarks ran against, the ground truth next to which your local setup looks pitiful. But that endpoint is also a runtime. It has a chat template you cannot inspect, sampler defaults you did not choose, a context policy you were never told, and possibly a quantization nobody will ever announce, running on hardware unlike yours and software very unlike yours.

It is not the model. It is a configuration of the model, chosen by strangers, that happens to be a good one.

Identical weights, different runtime defaults, and you have a different model.

Sit with that for a second. There is no canonical version of the thing you thought you downloaded.

The gift is that this is an unusually fixable class of problem, and the fix is boring: log the configuration. Sampler settings. Chat template hash. Actual context length used versus submitted. Quant format. Runtime and version. If your model got dumber on Tuesday and you cannot diff the config, you don't have a debugging problem — you have an archaeology problem, and archaeology is much slower and involves a great deal of guessing about pottery.

Then evaluate like you mean it. Three prompts at temperature zero is a zero-shot vibe check and a poor analog of anything agentic. Run several real benchmarks, chosen because they resemble your actual workload — long context, tool calling, domain knowledge — and run them against a configuration you wrote down. The point isn't to score the model. The point is to hold everything else still, so that when something shifts you can see which thing shifted.

Every implementation is a little bit broken. Yours, the lab's, the cloud's. The difference between a serious practitioner and someone yelling on a forum is not better hardware.

It's knowing which of your defaults you chose.
