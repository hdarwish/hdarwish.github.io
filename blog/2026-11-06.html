Your AI agent is an untrusted client, not a smart tool

The most dangerous bug in AI coding agents isn't hallucination. It's the silent exfiltration of identity metadata that happens because we treat LLMs as 'smart tools' rather than 'untrusted network clients'.

ai-agentssecurityprivacynetworking

When an agent makes an HTTP request, it is no longer 'thinking.' It is a network client. The moment it speaks HTTP, it is subject to the same security constraints as any other client: it must not leak identity, it must not trust the response, and it must not assume the server is well-intentioned.

The distinctionThe distinction between a *tool* (which you control) and a *client* (which talks to the outside world). A tool operates on local state. A client operates on network state. Treating a network client like a local tool is a category error that leaks data.

01

The Silent Passenger

Your AI coding assistant is likely sending your email address to every API endpoint it touches, and you probably didn't notice because it worked.

This isn't a hypothetical. A GitHub issue on the claude-code repository highlights a privacy violation in the User-Agent header. The agent, in its effort to be a helpful, well-behaved citizen of the web, is broadcasting its identity—and by extension, your identity—into the headers of every request it makes.

The mechanism is simple. The agent needs to identify itself to servers to handle rate limiting, debugging, or attribution. So it puts its name in the User-Agent string. But in doing so, it often includes metadata that links back to the human user. Your email address. Your session ID. The context of your work.

02

The Category Error

Why does this happen? Because we build agents as *smart tools*. We think of them as the smartest version of our own curl command. We assume that because the agent is 'ours,' the data it sends is 'ours' to control. We assume that because the agent is 'smart,' it knows when to send the email and when not to.

This is a category error. A User-Agent header is not a private message. It is a public broadcast. It is sent to the server, logged by the server, seen by intermediate proxies, and stored in access logs. It is a network artifact, not a local variable.

When you treat an agent as a tool, you optimize for *capability*. You want it to be able to talk to any API, any endpoint, any service. You don't add friction. You don't strip headers. You don't sandbox the network calls. You trust the tool to be smart.

But a *client* is not trusted. A client is an untrusted network peer. It is the same as a browser tab you didn't open. It is the same as a script you downloaded. It must be treated as potentially malicious, or at least potentially careless, because it is interacting with a world you do not control.

03

The Leak is in the Headers

The specific mechanism here is the User-Agent string. In standard HTTP, this is a low-stakes field. Browsers send it. Curls send it. It's usually a string like Mozilla/5.0 (Macintosh; Intel Mac OS X 10_15_7). It's not supposed to contain PII.

But agents are built by developers who want to be 'good citizens.' They want the server to know who is calling so they can debug issues, adjust rate limits, or provide better support. So they put the client ID, the user ID, or the email address in the header. It feels helpful. It feels like good engineering.

The metric here is *surface area*. Every header you add is a new channel for data exfiltration. The User-Agent header is one of the most widely logged and stored headers in the web. It is not encrypted in transit if the connection is not TLS (though it should be). It is visible to any intermediary. It is persistent in logs for years.

The consequence is that your identity is now tied to every API call your agent makes. If the agent calls a third-party API, that third party now knows your email address. If the agent calls a compromised API, the attacker now knows your email address. If the agent calls a server that logs all headers, your email is in that log.

04

The Fix is a Mindset Shift

The fix is not to remove the User-Agent header. The fix is to treat the agent as an untrusted network client.

This means: strip all identity metadata from headers by default. The User-Agent should be a generic string, like ClaudeCode/1.0. No email. No user ID. No session token. If the server needs to know who you are, it should use an Authorization header with a token, not a User-Agent header with an email.

This means: sandbox network calls. The agent should not have direct access to the internet. It should go through a proxy that filters out sensitive headers. It should not be able to make arbitrary HTTP requests. It should only be able to call pre-approved endpoints.

This means: log what the agent sends. You should be able to see, in real time, every header the agent sends to every endpoint. If you can't see it, you can't trust it.

The turn

The bug is not in the code. The bug is in the mental model. We built an agent that thinks in terms of 'helping the user,' but the network doesn't care about your intent. The network only sees bytes. And if you put your email in the bytes, the network will keep it.

Analogy A tool is like a hammer. You control it. You decide what to hit. A client is like a letter you mail. Once it's in the post, you don't control who sees it, who copies it, or who keeps it.

Where it breaks A letter is a one-way broadcast. A network client is a two-way conversation. The agent receives data back, which can also be a vector for exfiltration or injection.

If you're deciding
When
When building or deploying an AI agent that makes network calls
Prefer
Treat the agent as an untrusted client. Strip identity from headers. Sandbox network access. Log all outbound traffic.
Avoid
Treating the agent as a 'smart tool' that you can trust to make good decisions about what to send over the network.

The next time your agent makes a request, ask yourself: is this a tool I control, or a client I trust? If it's the latter, you're already leaking.
