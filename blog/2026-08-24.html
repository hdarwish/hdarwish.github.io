Your model isn't the bottleneck. Your loop is.

The strongest model on the market is losing users to cheaper tools. The FT reported it, and Hacker News spent 385 points arguing over whether the benchmarks are wrong or it's just price. Both answers skate past how strange the claim is. If capability were a property of the weights, the most capable weights would win every task, and cost would only decide whether you could afford to win.

Instead, weaker models keep beating stronger ones in the hands of actual users. Which means capability is not, or not only, in the weights.

This matters because of what teams do when their agent disappoints. They swap the model. They upgrade to the frontier tier, watch the bill triple, get a modest bump, and conclude that agents are two generations away from being useful. That diagnosis is expensive, and it is usually wrong, because nobody ever engineered the thing that was actually failing.

Half the industry says "harness" and means glue code. That's the error, and it's a load-bearing one.

Earendil's framing is the honest one: a harness is software that provides an environment for a model to operate within. Take the metaphor literally, because it pays. A climbing harness is straps and belts connecting you to ropes and carabiners; it secures you from falls, moderates your pace, and governs your route, and it carries the gear loops that let you bring the chalk bag and the nut tools up whichever wall you picked today. Royal Robbins on El Capitan is not a stronger human than Royal Robbins in the parking lot. He is a human plus a system that converts strength into ascent.

Where the analogy breaks — and it breaks in the most interesting place — is agency. A climbing harness never decides to place a quickdraw. The agent harness explicitly does not dictate when or how the model uses a tool; it describes the tools, makes them available, and hands the scheduling decision over. So the harness governs what is possible and what comes back, and cedes control of what happens next. Hold that thought; it's the whole hinge.

Four surfaces do the work. First, the system prompt — not the model's trained-in disposition (Claude Opus 4.5's widely publicized "soul document" is that), but something looser and more contingent, closer to the instructions a new employee gets on day one: not internalized, just followed while doing this particular job. It is injected alongside every prompt, which means it is not free. It occupies the same finite context as the transcript. Every sentence of policy you add is a sentence of working memory you take away.

Second, tools: capabilities written in code that the model can call, where the harness supplies both the description and the implementation. A web search. A write-and-execute-code tool. A compose-email tool. Note the asymmetry buried in there — you write the implementation for a machine, but you write the description for a reader who will decide, probabilistically, whether it applies. The description is the API.

Third, the loop, and Earendil's example is worth walking slowly because it's where the gears become visible. Picture a harness that lives in email, and a user who asks it to compare rankings and test scores of local primary schools. The model interprets "local," interprets "primary school," builds queries, fetches results — and then reviews those results against the original request and concludes, unprompted, that the first search didn't get enough. So it searches again. That second call, chosen rather than scripted, is the loop announcing itself. Then it decides to build a spreadsheet with the code tool, because all spreadsheets are just code wearing a grid.

Fourth, a translation layer, so the same harness can drive different models.

Read that fourth item again and notice what it does to the economics. If the model is swappable and the harness isn't, the harness is the asset and the model is a supplier.

Now go one level below the four-item list, because this is the floor real systems fall through. Every tool result comes back into the transcript. A search returns more text than you wanted. Code execution returns a stack trace, or twelve. Something decided how much of that to keep, what to drop, in what order, and what to say to the model when a tool simply failed. Nobody wrote a design doc for that decision. It got made anyway — by a default, by an if, by whoever wrote the string concatenation on a Friday.

So look at what you actually have. A process that cannot be preempted mid-thought, calling capabilities it interprets probabilistically, running under a hard memory ceiling, with an error path that decides whether a failure becomes recovery or becomes an infinite retry. You have built this machine before. It was your CI runner, your job queue, the exponential backoff you wrote once and never tuned.

Agent capability lives in the harness, not the weights. A harness is a control loop with a truncation policy. You've shipped several. They failed for exactly these reasons.

Sit with that for a beat.

Because it rewrites what "my agent is bad at this" means. Nearly every symptom you'd file under model stupidity has a harness reading. It forgot the constraint: your system prompt is competing for context with a bloated transcript. It picked the wrong tool: your description was ambiguous, and description is the API. It thrashed on a failing call: your error path returns the identical string forever, so the loop has no gradient to climb. It lost the thread halfway: something quietly deleted the middle and told the model nothing had been removed.

Here is the portable version. Before you upgrade the model, write your truncation policy and your error-recovery policy down as actual sentences that a colleague could disagree with. If you can't — if nobody knows what happens to a 400KB tool result — you don't have a model problem. You have an unengineered artifact sitting at the dead center of your product, and frontier tokens are just an anesthetic applied to it.

What would change my mind is a model that reliably recovers from a harness that lies to it — one that notices its own context was silently truncated and asks for the missing piece. I haven't seen that. Until then the ceiling is yours to raise.

The climbers already knew the good part: you own the harness. You choose what hangs on the gear loops, you adapt it to the terrain, you carry it to the next wall when the wall changes. Models will keep getting stronger and you'll collect that for free.

The loop is yours. Nobody is coming to tune it for you.
