sqliteexecutablessystems-design

What is the checksum of a binary that logs to itself?

There is a webserver whose visitor log lives inside its own executable. Not beside it. Not in /var/log. Inside the file you typed to start the process. You curl the homepage, and the binary gets one row longer.

Farid Zakaria's SELF format does this with a completely straight face: the program is a SQLite database, file server reports SQLite 3.x database, application id 1397050438, and sqlite3 server 'SELECT count(*) FROM presses' answers 0 until somebody clicks the button. Then it answers 1. Same file. Still executable.

Take the party trick seriously for one minute and it starts eating your operational assumptions from the inside. What do you back up? What do you diff? What does it mean for two machines to be running "the same build"? Every deployment system, every integrity check, every sha256sum in a CI pipeline rests on an assumption nobody bothered to write down — and this format breaks it on the first HTTP request.

Here's the machinery, because the machinery is the argument. SELF stores an ELF's segments as rows in a segments table. binfmt_misc matches the file, and the kernel does not execve your program at all — it execs an interpreter, self-exec, and hands it the path. The interpreter opens the database, maps the segments, jumps to the entry point, and passes argv + 1 through, so the program's own argv[0] is the path to the file it came from. Crucially, the interpreter releases its SQLite connection before jumping. It hands the program the keys and steps out of the room.

Which means the entire capability fits in one line of C:

int main(int argc, char **argv) {
  sqlite3 *db;
  /* the file the kernel just executed */
  sqlite3_open(argv[0], &db);
}

That's it. That's the whole exotic new power. A program that can open itself with write access.

The proof-of-concept, self-httpd, is three tables: routes (the website, inserted after compilation with readfile()), visits, and presses. Serving a page is SELECT body FROM routes. Logging a visit is INSERT INTO visits. The build pipeline is cc -O2 server.c -o server.elf, then elf2self, then a couple of sqlite3 invocations. New endpoint? Not a redeploy — a row: INSERT INTO handlers VALUES ('/api/busiest', 'SELECT path, count(*) FROM visits GROUP BY path ...'). Redbean needed an embedded ZIP and Lua hooks to reach the equivalent. Here the container is the database and the hook is a row.

I find this genuinely delightful, and I want that on the record before I start pulling on the loose thread.

The loose thread is in the flag. The demo starts with ./server --journal wal 8080, and if you know SQLite you already flinched, because write-ahead logging means there is now a server-wal and a server-shm sitting next to your "single file." The one-file promise leaks the instant you want decent write concurrency. Fine — that's a solvable annoyance.

The unsolvable one is what happens to the pages inside the file. SQLite owns that space. It allocates b-tree pages as the visitor log grows, splits them when they fill, parks freed ones on a freelist, and reuses them later for whatever needs room; a VACUUM will happily rewrite the entire file into a new page order. Your machine code and your visitor log are now roommates in one page-allocation arena, and the librarian deciding who sits where is a general-purpose database engine tuned for throughput, with no opinion whatsoever about the sanctity of your .text segment.

And the program keeps working perfectly, which is the part that should unsettle you. The interpreter doesn't seek to byte offset 0x1000; it asks for rows. Ask by key and you don't care where the bytes moved. So correctness survives the shuffling completely intact, and identity does not survive it at all. Those two properties have been welded together for your whole career by nothing more than the fact that files don't rearrange themselves, and SELF quietly unwelds them.

Think of a hardcover book that writes its own marginalia. Beautiful object, genuinely useful, and the ISBN on the back no longer identifies the copy in your hands. The analogy breaks in an important place — marginalia stays in the margins, whereas SQLite is free to rearrange the whole binding — and that break is exactly the problem.

Picture two servers, same elf2self output, deployed together. Give them a few minutes of real traffic and their checksums diverge. Neither is corrupted. Both are correct. Your fleet-integrity dashboard is now a random number generator, your backups contain production user data laminated into the code artifact, and rolling back the binary rolls back the visitor log with it. You cannot revert the program without reverting the state, because there is no seam left to cut along.

Sit with the fact that a running process holds its own executable open read-write, and something reorganizes. Immutable text pages, code signing, dm-verity, container image digests, diffing two builds, the entire question "is this the binary I shipped" — none of those are things we invented. Every one of them is a consequence of an invariant nobody ever had to argue for, defend in a design review, or even notice, because the filesystem was enforcing it for free the whole time.

Making the executable writable collapses code and state into one artifact you cannot defend.

Now the gift, which is better than the warning. SELF doesn't so much destroy that invariant as hand it to you, unbundled and explicit. The old one was file-shaped, which made it all-or-nothing and invisible. The new one is schema-shaped: hash the segments table and the routes table, ignore visits and presses, and you have a build identity that survives traffic. Backups become a query. "Are these two machines running the same code?" becomes a SELECT over a named subset of rows instead of a prayer about bytes.

Integrity stops being a property of the container and becomes a property you have to name. That's harder. It's also honest, and it generalizes far past one weekend project: most of the invariants holding your system upright are not in your code at all. They live in the substrate — the filesystem, the network, the scheduler, the clock — and you will never enumerate them by rereading your own repo, because you didn't write them and nothing reminds you they're load-bearing.

You find a load-bearing wall the way everyone finds one. Someone removes it, and the ceiling tells you.
