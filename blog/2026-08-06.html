The `if` was free. Your data was the problem.

Filter a million random floats. Keep 1% of them: 0.59 ms. Keep 50%: 3.94 ms. Keep 99% — nearly a hundred times more output than the first case, almost twice the output of the second — and it takes 1.49 ms.

Read that again. Same input, more work, less time. Every performance intuition most of us carry — less work is less time — predicts the exact opposite here, and misses by a factor of 2.6.

Serhii Potapov's benchmark is the setup for a better joke than the title of his post lets on. He calls it "making a filter 4x faster by removing an if." His own control experiment proves the if was never the cost. And once you see what actually was, you will start doubting a whole category of optimizations you have probably already shipped.

The code is the code you'd write. Idiomatic, boring, correct:

input.iter().copied().filter(|&x| x > threshold).collect()

First suspect: collect() doesn't know the output size, so the Vec grows and reallocates on the way. Every Rust dev has that reflex. Preallocate with Vec::with_capacity, push in a loop, measure again. At 50% kept: 3.87 ms, down from 3.94. Two percent. The reallocations were real and they were irrelevant, which is the most useful kind of negative result — it eliminates the answer you wanted to be true.

What's left is the CPU, and the CPU is not doing what your mental model says.

A modern core doesn't execute one instruction and then the next. It runs a pipeline dozens of stages deep, fetching and decoding instructions long before earlier ones have produced answers. That works beautifully right up until the instruction stream hits a fork: if x > threshold. Which way does the road go? Nobody knows yet — the comparison hasn't retired. And the core refuses to sit and wait, because waiting is death at billions of cycles a second. So it guesses, and it charges ahead down the guessed path doing real, committed, speculative work.

The branch predictor is a barista who starts your usual the moment you walk in. If you're a regular, the coffee is waiting when you reach the counter. If you order something random every day, the barista pours a lot of drinks down the sink. Where the analogy breaks: the sink isn't the expensive part. The expensive part is that the whole café has to be reset — pipeline flushed, speculative registers discarded, fetch restarted from the fork. On a typical modern x86 core that reset runs roughly 15–20 cycles. The comparison itself costs about one.

Now the table stops being weird and starts being arithmetic. At 1% kept, the answer is almost always "skip," the predictor learns "skip," and it's right 99 times in 100. At 99% kept, same story, mirrored. At 50% on uniformly random data there is no pattern to learn, so the predictor is a coin flip — wrong on roughly every second element, half a million flushes over the array. Half a million resets at 15–20 cycles each is on the order of two milliseconds of pure penalty, which is the same size as the gap between the 50% row and the 99% row.

So the cost isn't the branch. The cost is a branch whose direction is a random variable.

Which sets up an experiment so clean it should be taught in schools. Keep the same data. Keep the same threshold. Keep the same function — not one character changed. Sort the input first, outside the measured section, so the branch answers "skip" for the entire first half of the array and "keep" for the entire second half. That is a pattern even the dumbest predictor learns after exactly one miss.

Shuffled: 4.15 ms. Sorted: 0.93 ms. Four and a half times faster with the if still sitting right there in the source, untouched.

Hold that number, because it demolishes the framing of the whole optimization. The branchless version earns its speedup honestly — write the element to out[idx] unconditionally, then advance idx by (x > threshold) as usize, so the comparison becomes an integer add and there is no fork left to guess at. Real technique, real win. But it is not competing against a slow if. It is competing against entropy in the input distribution, and the if was merely the surface where that entropy got charged to your latency budget.

Branchless code does not buy you speed. It buys you variance reduction — and variance is something you should measure before you pay for it.

Look at what going branchless actually costs. In the 1% case, the branchy version runs at 0.59 ms because the predictor is essentially free labor: a tiny piece of hardware doing near-perfect work on your behalf, correctly skipping 99 out of 100 elements before you asked. Branchless throws that gift in the bin. It writes every element unconditionally, touches the full output buffer, dirties cache lines it will never need, and pays the same flat price whether your data is beautifully skewed or maliciously random. You are trading a distribution of outcomes — sometimes wonderful, sometimes awful — for one guaranteed number. That isn't an accelerator. That's insurance.

So the question stops being "is this hot path branchy?" and becomes "what does the data flowing through this branch actually look like, and how much does its shape move?" A query engine filtering on a clustered, sorted column gets predictable branches for free and should keep them, gratefully. The same engine filtering a high-cardinality column against an unhelpfully median threshold is the coin-flip case, and there the flat price is a bargain. Same source code, opposite verdicts, and the deciding fact lives in production data rather than in your repository.

The intellectual courage required here is small and very specific: before you rewrite anything, benchmark the hot path at several input distributions instead of one. If the timings fan out wildly — fast on skewed data, awful near 50% — you have a prediction problem and branchless is the cure. If they sit flat, the branch is already free and you are about to make your code uglier and your buffer hotter for nothing.

Performance intuition fails because we model the CPU as an obedient reader of our instructions. It isn't. It's a gambler with a very deep pipeline, and it plays your data, not your code.
