Your repo became a dataset. Git is the wrong abstraction.

In May 2026, Anthropic merged about 2,500 code changes per day. By September: over 30,000. They say the latent demand for merging code is practically infinite — remove one bottleneck and the merge rate climbs again. And the thing that broke first wasn't the code.

It was source control.

The bottleneck moved

Anthropic uses Claude to write software far more than almost any other company, so they're the first to see where tools built for human scale start to strain. They expect other heavy AI-coding shops to hit the same pressure points before long. Which means the wall they ran into is built out of assumptions you are standing on right now.

The wall has a name, and it's not "Git is slow." It's "Git assumes something that is no longer true."

Git's bet

Git is a decentralized system. Every clone is a complete, self-contained repository that can compute diffs, read history and blame, and check out any revision while fully offline. For the vast majority of repositories, this is the right design, and it's a large part of why Git became the standard. But a design that is right under one set of conditions is a bet: a wager that repositories are small enough to copy wholesale, and that the person holding a copy wants to work disconnected from everyone else.

At Anthropic, the history of the main branch alone is almost 100 GB. A compressed working copy is over 25 GB. They perform on the order of 25 million code checkouts per day for CI alone, before counting developer environments, agent sandboxes, and research jobs. Fetched naively, that's over 600 PB of Git traffic per day.

Six hundred petabytes a day is about seven terabytes every second, sustained, forever. That is not a workload. That is a weather system.

The apology layer

Git offers tools for working with a slice of a repository: shallow clones, sparse checkouts, promisor remotes. Beyond those, the standard monorepo playbook: internal mirrors and repository snapshot "seeds" kept in blob storage. Anthropic used all of them — at peak, they operated several hundred internal git mirrors to handle the load.

It bought time. But seeds fell further from the tip of main between refreshes, and operations that depend on history — diff, blame — took more and more care to keep working on partial clones.

Notice what all these workarounds have in common. Each one is an apology for the central design. Git says: the client should hold the whole world, offline. Every workaround is an elaborate way of saying "actually, you don't need the whole world, and you're not offline." At some point, the apologies cost more than the design they're apologizing for.

A server you can't take offline

So Anthropic designed from the opposite bet: clients are always online. Nearly all of their clients are agents and jobs that are online by definition. In Scion, the client maintains a bounded local object cache, lays out working copy files on disk, monitors filesystem changes, and gives users an ergonomic way to work with the server. Everything heavy — answering file history and blame, creating commits, performing merges and rebases — happens on the server.

The asymmetry is total. In Git, every client is capable of being a full-fledged server. In Scion, the client can compute very little on its own — but it needs very little data locally. The system draws on hard-won prior art from Google's Piper and Meta's Sapling.

Think of it like a database. The server holds the truth; a view is a projection you can query without holding everything. A working copy in Scion is a materialized view: the files on your disk are a cached, denormalized rendering of server truth. The analogy breaks in one interesting place — materialized views are read-only, while a working copy is something you actively edit and write back. So call it a bidirectional materialized view, the thing databases never quite give you.

And here is the part worth sitting with. With Git, a CI job or tool that needs to ask a question about the repository — who last changed this line, how are these two commits related — has to maintain a local copy of the repo or hope vendor-specific APIs provide the answer. With Scion, all the source control queries the client uses are exposed via API. In many cases, jobs don't need a local repository at all.

The snapshot was never the truth

Take a step back and see what the numbers add up to. A 100 GB history. A 25 GB working copy. Twenty-five million checkouts a day, all from programs that are online by definition. Git's model — copy everything, work offline, merge when ready — has a beautiful property: every clone is a complete world, and humans can go dark for hours. But nothing in this world is going dark anymore.

When a repo becomes a dataset, Git's core assumptions break.

Hold that thought for a beat. The moment it clicks is when you see that Scion is not a better Git at all. It's a caching and scheduling layer for a company-wide build graph. The server is the database. The clients are queries. The files on disk are the cache. Git's snapshot model is a ledger written for human hands at human speed — a record of what was, kept so people could coordinate. A dataset is a different creature: a surface to be queried, at machine speed, by machines.

Here's what this frees you to see, even if you never build a version control system. Every tool you reach for has an assumption about its world baked in, and the assumption only becomes visible when the world changes. Git assumed small, offline, human. When your repository becomes something else — a dataset queried by programs at program speed — you no longer have a Git problem. You have a data problem, and no amount of mirror tuning fixes that.

So ask your tools the uncomfortable question: what world were they designed for, and is that the world you live in now? When the access pattern changes, the abstraction must change. The past is a snapshot. The future is a query.
