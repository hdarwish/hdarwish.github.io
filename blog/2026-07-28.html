Your agent isn't getting smarter, it's getting wordier

There is a benchmark for whether an agent's code passes the tests. There is no benchmark for whether the codebase survives the agent.

SlopCodeBench is an attempt to stare straight into that gap, and its run on Opus 5 produced the most interesting boring result I've read all year. Correctness went up. So did line count. So did function count. So did complexity — and the write-up's own heading is blunt about how widely: "Complexity grows over time for all models." Not the weak ones. All of them, including the newest.

You should care about this before you fully understand it, because you are probably about to point one of these things at a repository that has to still be legible in three years. Every benchmark score you've used to justify that decision was computed on a codebase nobody had to maintain afterward. The score measured whether the patient survived the operation. It said nothing about how many instruments were left inside.

Here's the machinery. A coding benchmark needs an oracle: some automatic procedure that declares an attempt good without a human in the loop. Tests-passed is a magnificent oracle — cheap, decidable, uncheatable in the crude sense, and it emits a number you can drop into a table and sort. "Is this codebase pleasant to work in three years from now" is not an oracle. It's a dinner argument with no referee.

So think about spellcheck. Spellcheck won — it lives in every text box on Earth — not because spelling is the most important property of prose, but because a dictionary is a lookup table and "is this paragraph well-argued" isn't. We built the tool we could grade. Then, quietly, we started treating spelling as the thing writing was for. The analogy breaks in one useful place, and the break is the interesting part: a misspelled word sits there on the page, visible, embarrassing. Excess code hides. It looks like diligence.

Now climb inside the agent's episode. You have a task, a repo, and a test suite that will judge you the moment you stop typing. You hit an input that doesn't quite fit the existing code path. Two moves are available.

Move one: generalize. Find the abstraction that covers both the old case and the new one, rewrite the shared path, delete what you replaced. Move two: add a branch. Or a helper. Or a small parallel function that handles the new shape and leaves every existing caller untouched.

Move one is strictly more dangerous. Touching shared code can break a test that was already passing, and a broken passing test is a visible, scored penalty — a red mark in the only ledger anyone reads. Move two cannot break what currently works; additivity is its whole design. Its cost is redundancy, duplication, a rising complexity number, a fourth function that does almost exactly what the other three do. That cost lands after the episode ends, on a maintainer who does not exist inside the evaluation.

Which means the agent is optimizing with a discount rate of essentially infinity. Everything past the final test run is worth zero.

That asymmetry is the entire engine. Under a test oracle, inside a bounded episode, adding code is a variance-reduction strategy. It isn't sloppiness or weak taste. It's a rational bet against the only judge in the room, and it is exactly what you would do if you were graded solely on green checkmarks and knew with certainty you'd never open the file again.

Which is why the SlopCodeBench numbers land the way they do. The write-up doesn't say some of the output was bloated; the heading reads "almost all the code written triggered the slop meter," alongside "more correctness came at the cost of wayyy more code" and the flat observation that "these models write a lot of functions." Correctness and volume did not trade against each other. Volume was how the correctness got bought.

Here is the part I'd like you to sit with, because the tempting reading — models are crude now, the next release will have better taste — is precisely the wrong lesson. The trend line doesn't bend with scale. It bends with what's measurable, and no amount of capability changes the structural fact that tests-passed has an oracle and codebase quality does not.

Coding agents don't pass benchmarks by writing better code. They pass by writing more of it.

The uncomfortable implication isn't about the models at all. Decades of code review, refactoring culture, and "delete more than you add" folklore exist to teach human engineers to resist one specific instinct: solving a new case by bolting on a new case. Seniority, as far as I can tell, largely is the acquired appetite for the risky generalizing move over the safe additive one — the willingness to break something on purpose in order to leave less behind. And then we built an evaluation regime that rewards the additive move, at scale, monotonically, in every model we ship. We automated the junior engineer's failure mode and reported it as progress on SWE tasks.

So take the portable thing. Stop grading agent output on the snapshot and start grading it on the trajectory. A single diff that passes tests tells you almost nothing about judgment. Ten diffs in sequence, viewed through one question — did the codebase get smaller anywhere? — tells you nearly everything. If an agent has touched your repo twenty times and the function count has only ever risen, you don't have a collaborator. You have a very fast sediment layer.

You can make this operational without inventing the perfect quality oracle, which is the trap that keeps people from measuring anything at all. Log lines and function count per merged agent change. Plot complexity across the life of a module rather than per commit. Treat a monotone rise as a defect report about your process, not a law of nature. Then hand the model a task whose only success condition is deletion, and watch closely whether it can find something to remove. That's a real measurement, and unlike the leaderboard, it's yours.

What would change my mind? A model that holds its correctness score while its complexity curve goes flat. That would be the first honest evidence of judgment rather than throughput, and I would celebrate embarrassingly loudly.

Until then the benchmark numbers will keep climbing, and so will the line count, and the only oracle for whether any of it was good is still sitting in your chair, drinking your coffee, reading the diff.
