The bugs were the spec, and nobody wrote them down

Feed a forty-year-old COBOL program to an AI translator and it will hand you Java that reproduces the original's bugs exactly. That gets called a failure. I think it's the only part of the story that went right.

Because here is the awkward question nobody asks at the migration kickoff: when the new system disagrees with the old system, which one is wrong? You will say "whichever one violates the requirements." Lovely. Show me the requirements for a 4,000-line COBOL program that has been in production since before the euro existed. Not the intent, not the tribal memory of the two people who still know it — the document. The one that says what should happen when a field overflows, or when a rounding step truncates instead of rounding half-up, and some reconciliation team quietly built a compensating adjustment around it fifteen years ago and then retired.

That document does not exist, and its absence is the entire project.

The stakes here are not academic. If you "fix" that truncation during migration, you do not get a correct system; you get a system whose outputs no longer match the ledgers, the reports, the regulatory filings, and the compensating hacks of every consumer downstream. Congratulations: two bugs, one of which is invisible and distributed across four departments.

What makes this newly interesting is a paper attacking the genuinely hard problem, which is not translation. Ferenczi, Docherty, Bessonov, Findlay and Lingamneni describe what they call the Locksmith Loop: an agentic test-synthesis method for validating COBOL-to-Java migration. The setup is the delicious part. They stand up two runtime environments — the COBOL source and the generated Java target — each instrumented with mocks so both run off-mainframe on commodity hardware. The mocks are doing more than portability work: they pin down every edge where the outside world leaks in, so the same input produces the same answer twice. Determinism is not a nice-to-have here. It is what makes comparison mean anything at all.

Then they let an agent go hunting, and the hunt has a name: Witness Search. The agent searches over the input mocks trying to penetrate program branches — not to prove the program is good, but to find an input that reaches a piece of code nobody has reached yet. Each such input is a witness. It then applies parity-preserving mutations: variations on that input that should leave both implementations in agreement, which is how one witness becomes a family of them. Run the input through COBOL. Run it through Java. Compare. That comparison is the whole trick, and it's why the authors get to call this a deterministic oracle rather than a vibe check.

Think of it less as testing and more as locksmithing, which is presumably where the name came from. You are not asking whether the lock is a good lock. You are asking whether your copied key turns it exactly the way the original key does — including the spot where it sticks.

When the search stalls, the method does something I genuinely admire. Instead of shrugging at a coverage plateau, an analyzer identifies a Locked Paragraph: a specific condition preventing deeper exploration. The unreached code gets named and characterized rather than silently dropped off the report. Across three case studies — two open-source programs and one internal production-like COBOL program, ranging from 430 to 4,114 source lines — this pushed past the ceiling plain input search hit: near-complete coverage on the open-source pair, 91.90% branch coverage on the production-like one. And in every accepted test case, the generated Java matched the COBOL reference under deterministic parity checks.

Read that with the right emphasis. The oracle is not a specification; the oracle is the old program.

Which means the pass condition is agreement, not correctness — and agreement includes the rounding error, the off-by-one in the boundary case, the branch that returns a stale value under some condition nobody has articulated since 1994. The analogy I keep returning to is manuscript transcription: the scribe who silently corrects the original's spelling has destroyed evidence, while the scribe who copies the error faithfully and marks it [sic] has preserved something a scholar can actually work with. The analogy breaks in exactly one place, and the break is the interesting bit — a manuscript has no downstream consumers who will wire money based on its typos. Your COBOL does.

The moment you accept that observed behavior outranks intended behavior, the hard part of migration stops being the language. Java versus COBOL is a solved-ish problem; an agent can grind through it. What replaces it is stranger, and much less fun to put on a slide: you now have to discover which wrong answers are load-bearing.

In a legacy migration, the bugs are the specification. Reproducing them is success.

Sit with that before you argue with me.

The scandal was never that a machine copied the bugs. It's that after decades of production nobody had written the bugs down as requirements — so a machine had to rediscover them by brute-force witness search, one branch at a time, and then a human had to stare at 91.90% and decide whether the missing 8.10% was the boring 8.10% or the part that clears payments. That is a real decision with a real cost, and no oracle makes it for you. The Locked Paragraph doesn't remove the judgment. It just refuses to let you make it by accident.

So here's the portable piece. Stop asking your migration "is the new code correct?" It's unanswerable, and it invites people to be helpful in the worst possible way. Ask instead: where does the new code differ from the old, and for each difference, who did I ask? Differences become a reviewed list with names attached. Fixes become deliberate, dated, separately deployed changes — after parity, never during it. That isn't conservatism. That's refusing to smuggle a behavioral change inside a rewrite where nobody will ever find it again.

And it reframes the deepest thing about old software: a system that has run for thirty years is not a description of what anyone wanted. It's a fossil record of everything the world actually did to it.

Copy the fossil. Then, in daylight, decide what to mend.
