Your Coding Agent Is Taking an Archaeology Exam

The leading agent in Real-SWE resolves only 38.8% of tasks. One of those “coding” tasks requires reconstructing tax exemptions, jurisdiction rules, calls to an external authority, invoice state, and ledger reconciliation before making the right change. The strange part is not that the patch is difficult; it is that writing the patch comes after discovering what the software is supposed to mean.

The code may be the smallest part of the problem.

The specification is scattered

Real-SWE’s conspicuous choice is private repositories, which reduce the chance that a model encountered the code during training. But privacy is only the drawbridge. Once inside, the agent faces company-specific rules distributed across implementations, tests, schemas, API contracts, configuration, naming conventions, and assumptions previous developers considered too obvious to record. No file contains “the specification” because the specification has leaked into the entire repository.

If you read the resulting score as “how well the model programs,” you will buy the wrong capability and diagnose failures at the wrong layer. A failed task might reflect weak inference, but it might equally reflect poor retrieval, truncated tool output, bad repository navigation, or an inability to decide which source is authoritative. Prompt polishing will not repair a system that never found the decisive test.

A tax fix is an investigation

Consider what the tax task demands. An exemption is not merely a Boolean waiting to be flipped: its validity depends on jurisdiction, an external authority may supply or verify information, the invoice occupies a particular lifecycle state, and any correction must remain consistent with the ledger. Changing one branch without recovering those relationships can produce locally plausible code that is globally false—the software equivalent of repairing a clock by removing the gear making the irritating noise.

The clock analogy earns its keep because every gear constrains the others. It also has a limit: business software is worse behaved than a clock. Some constraints live outside the machine, in regulations, remote services, historical data, and organizational decisions that changed while the code retained the old names.

The agent must therefore build an evidence chain. It locates the entry point, follows calls across modules, identifies authoritative data, inspects tests for encoded expectations, distinguishes intended behavior from accidental behavior, and checks that the patch preserves invariants elsewhere. Miss one link and task-resolution rate falls even if the model generates flawless syntax, because syntactic correctness cannot rescue a false account of the business rule.

A superb code completer with poor repository navigation is not a mediocre agent. It is barely an agent.

Picture a detective arriving after the crime, except the witnesses are type definitions, the security camera is a test suite, and the suspect has been renamed twice. Generating the patch is writing the arrest report. Most of the work is establishing what happened, which witness is credible, and whether the proposed culprit could even have reached the scene.

The analogy breaks at one important point: detectives usually know which sources count as evidence, while a coding agent’s harness decides what evidence exists from the agent’s perspective. Search commands, file viewers, symbol indexes, test runners, context windows, edit formats, and retry policies control which clues reach the model and in what shape. Change those tools and you change the probability that the same model reconstructs the rule correctly.

The harness chooses reality

A model handed one giant repository dump receives abundance without direction: relevant definitions compete with generated files, obsolete paths, repeated names, and unrelated code for limited attention. Iterative search permits a different mechanism. The agent can form a hypothesis, inspect a symbol, trace its callers, run a targeted test, revise the hypothesis, and search again; useful context is selected by inquiry rather than accumulated by shovel.

That distinction moves the metric that matters: successful task resolution. More context can increase noise, while better-selected context can expose the one invariant that makes an apparently reasonable patch impossible. The engineering consequence is wonderfully inconvenient for anyone selling enormous context windows as bottled understanding: harness design should optimize evidence quality, not merely token volume.

Tests matter twice. After an edit, they evaluate behavior; before an edit, they are executable fragments of institutional memory. A test may reveal that an invoice state permits recalculation, that an exemption must survive reconciliation, or that an external response outranks a cached field. Running tests only at the end discards a diagnostic instrument, while choosing and interpreting them during the investigation turns failure output into another round of evidence.

Tool behavior also changes what “reasoning” can accomplish. If symbol search exposes callers cleanly, the model can trace an invariant through the repository; if results are truncated, generated code is hidden, or command output loses crucial structure, the model may construct a coherent explanation of the wrong subsystem. The score then moves with indexing, output formatting, permissions, and iteration policy.

Those tools are not parsley sprinkled around the intelligence. They participate in it.

The leaderboard changes identity

Once success requires recovering a private organization’s rules from partial evidence, and once the available evidence and inspection order are controlled by search, execution, editing, and feedback tools, the thing being evaluated no longer sits entirely inside the model, however convenient that fiction may be for a leaderboard.

Enterprise coding benchmarks measure context recovery more than code generation.

The leaderboard therefore ranks model-and-harness combinations, whether the column heading admits it or not. This does not weaken Real-SWE. It makes the benchmark more faithful to enterprise software, where correctness means recovering the local constitution before proposing an amendment—and where a beautifully written amendment can still violate three clauses nobody thought to show you.

Evaluate the expedition, not just the explorer

When comparing agents, ask what evidence each system can acquire and how it can challenge its own interpretation. Can it search by symbol and text, inspect callers, run a narrow test before a broad suite, notice that an external authority outranks a cached field, and preserve a trail from requirement to code path to verification? Those questions separate inference failures from context failures and expose a harness that handed the model a teaspoon before pointing toward an archaeological site.

The portable principle is to improve the recovery loop before demanding prettier generation. Make authoritative sources discoverable. Keep tool output legible. Expose repository structure, let tests answer intermediate questions, and judge whether the final change preserves business invariants rather than merely compiling. Better typing is useful; better evidence changes what can be known.

Do not ask only, “Can this agent write the fix?” Ask, “Can it discover the law the fix must obey?”

The coding agent that matters will not win by typing faster. It will win by learning where your organization buried the truth—and how to dig without breaking it.
