One Codebase Was Never One Platform

Shopify went all-in on React Native in 2020 and later called the bet extremely successful. It reaffirmed that direction in January 2025—and is now moving its mobile future back to Swift and Kotlin.

What became more expensive than maintaining two codebases?

Not React Native, exactly. Shopify says its apps are fast and the framework delivered what it promised: features built once, broader developer participation, and less effort spent chasing parity. What changed was the price of the alternative. Coding agents made duplicated native implementation cheaper, exposing costs that the shared codebase had never abolished.

The seductive arithmetic of one

The original calculation was sensible. If iOS and Android require separate implementations, every feature appears twice in the engineering ledger: twice to write, twice to review, twice to keep aligned. A shared React Native implementation reduces duplicated code, lowers the risk that one platform trails the other, and lets more developers contribute without first mastering both native stacks. If implementation effort and feature parity dominate the decision, centralizing the code is excellent arithmetic.

But “write once” describes where product logic is authored, not where the product must behave. The application still lands on two operating systems with different capabilities, first-party tools, performance characteristics, release machinery, accessibility behavior, and evolving APIs. React Native stands between shared code and those platforms, translating enough of their differences to make one implementation useful.

Picture two countries with different tax laws. A cross-platform framework is not a treaty abolishing both tax codes; it is an excellent accounting firm that gives you one interface and handles much of the translation. You still pay when either country changes its rules, when a case falls outside the common form, and when the translation machinery itself must be updated. The analogy breaks because React Native supplies real runtime and UI machinery, not merely paperwork—but the ownership pattern is the same.

The laws remain.

Where the second codebase went

Shopify names the deferred bill plainly: significant time and resources went into performance optimization, foundational React Native work, framework updates, and external dependencies. None of that means the framework failed. It means duplication was exchanged for mediation. Instead of implementing every feature twice, engineers maintained the layer that allowed one implementation to serve two platforms.

That exchange moved different metrics in opposite directions. Shared implementation reduced feature-building effort and parity drift; mediation increased framework maintenance, dependency coordination, and distance from first-party platform tooling. As long as the first saving outweighed the second cost, React Native won—and Shopify says that for years it did.

Architecture diagrams are shameless little accountants. They count visible boxes and ignore obligations. A single shared feature box looks cheaper than separate iOS and Android boxes, while framework upgrades, dependency compatibility, performance tuning, platform-specific foundations, and escape hatches disappear into one innocent arrow labelled “React Native.” The complexity is not gone; it has merely acquired less legible stationery.

A codebase count is not a cost model.

Agents changed the denominator

By late 2025, Shopify found that coding models were no longer merely accelerating isolated tasks. In prototypes, agents could implement an Android feature using its iOS version as a reference, or travel in the other direction. Shared specifications, tests, and review checkpoints reduced the human work required to preserve parity, while developers could contribute beyond their primary stack more effectively.

The duplication got cheaper without pretending the platforms were identical.

Think of a musical score performed by two orchestras. React Native shares more of the performance machinery; the agent-assisted native approach shares the score, then produces platform-specific parts for strings here and brass there. The analogy breaks because software specifications are rarely as complete as musical notation, which is precisely why Shopify still names testing and review as part of the process. Translation is cheaper, not infallible, and the conductor has not been replaced by a cheerful autocomplete.

Native still means building and maintaining software twice. Shopify explicitly says that cost has not disappeared. What changed is the machinery around that duplication: implementation and cross-stack translation can be assisted, while specifications, tests, and review checkpoints help detect divergence. The relevant metric is no longer raw file count but scarce human attention; the consequence is that duplicate native code may cost less than maintaining a central abstraction between the product and both platforms.

Once shared implementation stops dominating the cost equation, years of perfectly rational investment in a framework can become less attractive than letting each platform own its implementation, because the framework must continue absorbing platform change while its largest economic advantage quietly shrinks.

A shared codebase defers platform complexity; it does not eliminate it.

Price the boundary, not the files

The useful question is no longer “Do we want one codebase or two?” That counts artifacts rather than obligations. Ask where platform differences are handled, how often that boundary must adapt, what distance from first-party tools costs, and whether duplicated implementation still consumes primarily scarce human attention. Then ask the impolite question architecture discussions often avoid: which cost is falling fastest?

This prevents the silly conclusion that Shopify has proved React Native bad. Its account says nearly the opposite: the framework succeeded under the economics of 2020. A later capability changed one of the decision’s load-bearing assumptions, so the correct architecture changed with it. Refusing to revisit a successful choice would not be consistency; it would be loyalty to an expired price tag.

The portable idea is to separate shared intent from shared implementation. Specifications, tests, review checkpoints, and platform examples can carry parity without requiring both platforms to inhabit the same abstraction. Whether that model works elsewhere depends on the quality of those artifacts, the frequency of platform divergence, and the real maintenance cost of native code—not on fashionable declarations that agents have eaten software engineering.

Complexity always sends an invoice. Read the return address.
