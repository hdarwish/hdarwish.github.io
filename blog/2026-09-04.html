Perfect precision, unmoved recall: the number everyone skipped

A tool so good the agent won't touch it

Give a coding agent semantically precise code navigation — real references, real definitions, the kind of thing that can tell a function call from the same word sitting in a comment — and on simple localization tasks it will pick that tool between 0% and 6% of the time. Force it down the semantic path first and task success falls, from 100% to 89%. Pengcheng Xu's small study measured exactly this across three Claude models and a handful of Python and TypeScript repositories.

The comfortable reading is that models are lazy, or badly trained, or sentimentally attached to grep because the internet is full of it. That reading is wrong, and buried in the same study is a pair of numbers considerably more uncomfortable for anyone building retrieval for agents.

Precision is the thing that demos well

Semantic search, AST indexes, LSP bridges, embeddings over the monorepo — whatever you are building, you are almost certainly optimizing precision. Precision is legible. Precision goes on a chart and the chart goes up. And on the task you care most about, this study suggests precision was never the constraint.

The agent isn't lazy, it's routing

Kill the laziness story first, because the data won't support it. On reference-completeness tasks — find every caller of this function — the same models chose semantic navigation 45% to 57% of the time, unprompted: Opus at 45%, Sonnet at 50%, Haiku at 57%. Same tools, same free choice, and the routing flips completely with the shape of the request. Localization: 0-6%. References: roughly half. That is not a habit. That is a policy, and it is a defensible one.

The repository mattered as much as the task. On remeda, a clean TypeScript project where grep's precision was already 1.00, LSP-backed navigation delivered +0.000 F1 and cost 16% more tokens. On hono — same language, same tooling — grep's precision collapsed to 0.51, and semantic navigation bought +0.246 F1 while spending 12% fewer tokens. Python's requests landed in between: grep precision 0.76, +0.072 F1, +19% tokens.

Read those three rows again, because together they demolish a folk theory. The predictor of semantic navigation's value is not whether the language has strong static types — two TypeScript repos, opposite verdicts. It is how lexically noisy the codebase is: how many places a symbol's name shows up meaning something else. Short generic names, heavy re-export barrels, docs and fixtures full of the same tokens, and grep's precision falls through the floor while the semantic tool suddenly earns its keep.

So you cannot ship the fancy retrieval path as a global default; its value is a property of the repo, and you can measure it in an afternoon.

The interface was doing more work than the backend

The next finding is the one I find genuinely delightful, because it isolates a variable so cleanly you could teach an experimental design class with it.

The LSP-backed tools initially returned a location and nothing else: file, line, column. Correct, precise, and useless on arrival — the agent had to open the file to find out what was actually sitting there. grep, by contrast, hands back the matching line immediately: src/auth.ts:42: return validateToken(token). Xu changed the semantic tool to include the source text in that same shape. Same backend, same set of references, identical precision. Only the payload changed.

Pass@1 on multi-file rename went from 0.67 to 0.83. Follow-up file reads per episode fell from 15.2 to 3.2.

A tool that returns a pointer instead of a value has outsourced its own work to the caller. Picture a librarian who answers "where's the passage about tariffs?" with a shelf coordinate, versus one who hands you the open book with a finger on the line. Both are accurate. One costs you a walk across the building, fifteen times. The analogy breaks in exactly the instructive place: the librarian's walk merely wastes time, whereas the agent's walk burns context window — and context is the substrate the agent thinks in. Making it fetch isn't just slow. It makes it stupider on arrival.

The number nobody put in the headline

On reference-completeness, semantic navigation lifted precision from 0.76 to a flawless 1.00. Every false match gone. If retrieval quality were the thing standing between an agent and a complete list of callers, that intervention should have cracked the task open — and it should have paid for itself in tokens saved rather than tokens spent.

Recall stayed near 0.66 in both arms.

Both arms. Perfect precision surfaced not one additional true caller that noisy text search had missed. The gap was never made of bad matches getting in the way; it was made of callers the agent never went looking for — the re-export it didn't follow, the test directory it didn't consider part of the job, the second package in the workspace. When precision goes to 1.00 and recall refuses to budge, the subject has quietly changed from tools to effort.

Better retrieval precision cannot fix an agent that stops looking too early.

Hold there a beat, because it relocates the entire bug. One third of the callers are missing and the index is innocent.

What this frees you to build instead

The missing third lives in the harness. It is a question of whether the loop has a stopping criterion worth respecting: does the agent enumerate candidate files before it starts, keep a ledger of what it has covered, notice that a symbol is re-exported under another name, get asked "are you finished, and how would you know?" No retrieval tool can answer that, because a retrieval tool only ever sees the queries it was handed. Thoroughness is not a property of search. It is a property of the search policy.

Which gives you a triage order, if you have a clever tool and a disappointing eval. Measure your grep baseline's precision on your actual repository — if it sits near 1.00, your semantic layer is 16% token overhead in a lab coat. Then check whether your tool returns values or coordinates, since that fix cost nothing but a payload change and moved pass@1 by 0.16. Only after both of those should you go hunting precision, and when you do, watch recall like a hawk. If recall doesn't move with it, you have been sharpening the knife while the cook keeps wandering out of the kitchen.

Precision is a promise about what you found. Recall is a confession about when you stopped.
