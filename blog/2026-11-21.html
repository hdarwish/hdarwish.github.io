Redis's fastest structure was its biggest memory hog

The Sacred Relic

For over a decade, the Redis skiplist was treated as a monument to high-performance engineering. It was the structure that made sorted sets fast, the one that survived the original architecture review, and the one that almost no one dared to touch. It was a latency hack that quietly bankrupted memory efficiency.

That silence was expensive. Every sorted set larger than the listpack threshold was paying a hidden tax on RAM, not in obvious spikes, but in the quiet, constant accumulation of pointer overhead. We optimized for speed so aggressively that we stopped looking at the cost of holding the data in the first place.

The Invisible Tax

Why did this tax go unnoticed? Because the skiplist’s design is architecturally elegant in a specific, narrow sense: it pairs a hashtable for O(1) lookups by member with the skiplist for O(log n) ordered lookups by rank or score. It solves the problem of finding data quickly. It does not solve the problem of storing data cheaply.

Look at the raw bytes. A standard skiplist node carries a backward pointer (8 bytes), plus an average of 1.33 levels of forward pointers and span values. Since skiplists are probabilistic, each node has a 25% chance of gaining another level. Each level costs 16 bytes (8 for the pointer, 8 for the span). Add the 8-byte score, and you are looking at roughly 37 bytes of overhead per node before you even count the member string itself.

This isn't just dead weight; it’s a cache killer. Modern CPUs rely on L1, L2, and L3 caches to avoid the ~100 ns penalty of a DRAM access. A skiplist is a chain of separate heap allocations. Following the structure means dependent fetches: you have to read a pointer to know where to read next. A 2025 study of concurrent in-memory indexes found that traditional skiplists suffered 2.4–4.8× more cache misses than comparable B-trees, resulting in 2–8× lower throughput. We were paying for speed in latency, and we were paying for it again in memory.

fbtree: The 61-Way Fix

Valkey 9.2 replaces the skiplist with fbtree, a high-fanout B+ tree variant. The core shift is structural: instead of one element per node, fbtree packs up to 61 entries into a single 512-byte leaf node. This is the difference between a file cabinet where every drawer holds one paper and a warehouse where every shelf holds a box of sixty papers.

The fanout matters for two reasons. First, it slashes the per-member pointer overhead. Second, and more critically, it reduces the number of levels you must traverse. The skiplist has an effective branching factor of about 4; fbtree’s is 61. Both are O(log n), but the B+ tree has substantially fewer levels to traverse, meaning fewer opportunities for expensive, dependent memory fetches. A 5-million-member test showed a 36–43% reduction in per-member memory overhead, saving up to 109 MB.

fbtree also optimizes the lookup path. Inner nodes store a four-byte "feature" alongside each anchor, allowing the CPU to use SIMD instructions to compare features in parallel. Often, the correct child is identified before the child node is even fetched. For range scans, leaf nodes are linked in a doubly-linked list, allowing sequential traversal without climbing back up the tree. It is a data structure that has been explicitly designed for the memory hierarchy of modern hardware.

The Admission

We spent years treating the skiplist as the pinnacle of in-memory performance because it was fast to read. We ignored that it was expensive to keep.

The 43% reduction isn't a minor optimization; it's the admission that the 'fastest' data structure in Redis was actually the most wasteful one in the stack.

When you optimize for one metric in isolation, you create a liability in another. The skiplist bought us microseconds of lookup time at the cost of megabytes of wasted RAM and cache coherence. We were building castles on sand, and we didn't notice because the sand was very, very fast to walk on.

The Portable Lesson

The lesson isn't that B+ trees are always better than skiplists. The lesson is that "low latency" is not a monolithic goal. It is a vector with multiple components: cache locality, allocation density, and branch prediction. When a data structure trades density for speed, it imposes a tax on every other component of your system's memory budget.

Next time you reach for a "fast" data structure, ask what it costs to sit idle. The most expensive line of code is often the one that does nothing but hold a pointer to a place that isn't there.
