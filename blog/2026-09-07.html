The bug wasn't in the silicon. The page was executable.

A hypervisor that dies quietly

Every hypothesis in this debugging story is reasonable. Every technique is competent. The answer is none of them.

In a writeup published on purplesyringa's blog, Sonya is building a bare-metal ARM64 hypervisor for postmarketOS. Enable the CTR_EL0 intercept — the entire point of the project, so not optional — and the phone randomly locks up. Watchdog fires, system resets. Disable the watchdog and it hangs instead, which at least kills the "boot just got slow" theory. Then comes the real work: singlestepping the whole exception handler in QEMU, where it behaves exactly as written; auditing the stack allocation; padding out all sixteen slots of vbar_el2 with bl unknown_trap so that any unexpected exception prints X30 and ELR_EL2 and confesses itself; reading /proc/last_kmsg from the corpse of the previous boot; grepping a stripped kernel image with objdump -D -b binary for ctr_el0 and hand-patching all 22 matches.

None of it finds the bug.

The failure mode emulation cannot reach

You have very likely shipped this class of bug without knowing, because it didn't crash. The failure mode isn't "wrong answer." It's "the CPU cheerfully executes bytes that no longer exist anywhere except a cache" — behavior that is not merely incorrect but unreproducible under emulation, because QEMU models an instruction cache that is coherent with memory and real ARM cores do not promise you one. Your debug prints can't rescue you either, since the handler that would print them isn't the handler actually running.

Three different programs, all of them yours

The immediate cause is a two-line architectural detail with an enormous blast radius. On AArch64, instruction caches are not coherent with data caches. Write bytes through the normal data path and they land in the D-cache; the I-cache has no idea and no obligation to find out. The architecture requires you to say so explicitly — clean the data cache to the point of unification, invalidate the instruction cache, insert the barriers — or the fetch unit keeps serving whatever it remembers from the last time it looked.

Now the offender:

msr_accessor_sort(
  msr_accessors,
  ((uintptr_t)msr_accessors_end - (uintptr_t)msr_accessors)
    / sizeof(struct msr_accessor)
);

That array contained machine instructions. Sorting it at runtime rewrote executable code through the data path. So the phone ran the pre-sort layout out of the instruction cache while the D-cache and RAM held the post-sort layout: the code that was compiled, the code in memory, and the code being executed were three different programs, and no component in the system considered this worth mentioning.

Sonya finds it, moves the sort to build time, and the debug prints finally show the handlers working as intended. The system still doesn't boot. That's the cruelest available outcome — correct diagnosis, correct fix, bug survives — because the same structural mistake was sitting somewhere else, in the stack, declared in .data:

.section .data.stack
.p2align 12
.long 0
.p2align 12
stack:

Nothing wrong with that code. Everything wrong with that section's permissions.

The oracle you already own and refuse to switch on

Think about what a page-permission bit actually is. We market NX as a wall: attacker sprays shellcode into a buffer, the buffer is non-executable, the exploit dies. True, and boring. Structurally it is something else entirely — a machine-checked assertion about your own program. Instructions never come from here. An assert() the hardware re-evaluates on every single fetch, at zero marginal cost, forever.

Compare it to a type system. A type annotation doesn't stop a malicious caller; it stops you, in the moment you confuse two kinds of thing. NX is that idea projected onto physical address space, with one upgrade: no cast gets around it. The analogy breaks in a way worth naming — a type error is caught before you ship, an NX fault is caught at runtime, on device, possibly in someone's pocket. But that's precisely the trade you want here, because a coherency bug is invisible to static analysis and invisible to emulation. Runtime is the only place it exists.

Here is what NX buys in this specific hunt. Mark the data section non-executable and the first fetch from that region raises a permission fault; the fault lands in one of those sixteen bl unknown_trap slots that were already wired up; the address prints. Instrumentation Sonya had already built. A report she never received, because the hardware had been given permission to stay quiet.

Without NX, the fetch succeeds. It returns whatever the icache happens to be holding — stale bytes, plausible-looking nonsense — and the CPU executes it. No exception, no log line, just a phone that stops and a watchdog reset, and an engineer forming the entirely rational hypothesis that ARM vendors ship out-of-spec silicon.

So the difference between "three days of suspecting the CPU" and "one fault with an address in it" was not a debugger, not a logic analyzer, not a better mental model of cache maintenance. It was one bit in a page table entry that the project had skipped, because the threat model contained no attacker.

Security bits earn their keep as debugging oracles, not as attack mitigations.

Sort your hardening by the faults it makes loud

Stop ranking mitigations by threat model and start ranking them by which invariant they convert into a loud fault. W^X isn't only anti-exploitation; it's the cheapest available detector for "my program is executing memory it never intended as code." Guard pages don't merely stop overflow attacks; they turn a stack overflow from silent corruption of whatever was adjacent into an immediate fault with an address attached. Read-only .rodata catches your own stray writes long before it catches anyone else's. Every one of these is a nondeterminism-to-determinism converter that we have mislabeled as a lock.

The reframe worth carrying: when you skip a hardening feature on a bare-metal or embedded target because there's no adversary in the picture, hear what you are actually choosing. I am making my future bugs invisible. On a platform that gives you no cache coherency guarantee, that is close to self-harm.

The best security features were never really about the adversary. They're about the fact that a CPU will do exactly what you permitted, including everything you never meant — and the only way to be told is to have said no in advance.
