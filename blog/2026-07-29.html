Your buttons-versus-links rule died the moment you clicked Log Out

Clicking "Log out" navigates your page to a logged-out one. It is still a button. Clicking a mailto: link navigates nothing at all — it pokes some desktop email client you forgot you installed. It is still, correctly, a link.

Whatever rule you learned about buttons versus links, it just failed twice in one sentence.

This is not a taxonomy squabble, because the rule everyone learned — links navigate, buttons do things — is the rule that produces the two most common UI crimes on the web. On one side: the <a href="#"> that deletes your account, unbookmarkable and unexplainable, sitting there in the costume of a destination. On the other: the "Next Page" control implemented as a button, which you cannot middle-click, cannot copy, cannot send to a friend, because someone decided pagination was an action. Same wrong test, two directions.

The real test is about who owns the context.

A link's semantics do not say "this changes the page." They say: this is an independently navigable destination — a thing with an address, a thing that exists apart from the click that reached it. That promise is machine-readable, which means browsers can build features on top of it without asking any website's permission. Hover to preview the target. Middle-click for a new tab. Right-click and get a context menu stuffed with link-specific verbs: copy, open in window, save, share. None of that is in your HTML. All of it is the browser cashing in on a guarantee your markup made.

The guarantee cuts both ways, which is why the fake link is dangerous rather than merely untidy. An href is a GET, and GETs are supposed to be safe and repeatable, so crawlers follow them, browsers prefetch them, and proxies cache them. Dress a destructive action as a destination and you have invited every one of those well-behaved machines to fire it for you, unprompted, at scale.

The best detail in this whole argument is historical: the hyperlink predates the browser tab. When browsers invented tabs, no website had to do anything. Not one line of code. Because links represented re-contextualizable destinations, browsers could invent a brand-new context and drop every existing destination into it. Every site on earth got a massive feature upgrade for free, overnight, retroactively. We used to open each Wikipedia article in its own window. Imagine.

Now look at what a button doesn't have. No hover preview, no middle-click, no copy-the-action, and a context menu that tells you nothing about where the button goes — because the button doesn't go anywhere you're allowed to know about. It fires inside one specific browsing context, almost always the current one, and that is the end of the story.

A link is a street address. A button is a doorbell. You can write an address on a postcard, hand it to a stranger, bookmark it in a notebook, come back in a year and it still means the same thing; that portability is re-contextualization. A doorbell means something only while you're standing in front of that particular door. There is no way to copy a doorbell. The analogy breaks in one place worth naming: addresses go stale and doorbells don't, which is exactly why link rot exists and "button rot" doesn't. The price of portability is that portable things escape into the world and outlive what they pointed at.

Run the messy cases through the context test and watch it hold where the navigation test collapsed. A fragment link jumps within the current page — no navigation, but a genuine destination you can bookmark and mail to a colleague. A download link saves a file — no navigation, and still perfectly copyable. A search button sends you to results — but the action belongs to the form's current state, not to any shareable address. A logout button navigates — and "log out" bookmarked, then clicked from a stranger's email, is at best nonsense and at worst a small attack.

Navigation is noise. Context is signal.

Take the plainest case: an edit form with Save, Save as draft, Cancel, and Delete. People make Cancel a link constantly, because cancel "just goes back," and going back feels like navigating. It isn't. Cancel's job is to close this edit view, the one you are in, right now. Dressing it as a link lies about its purpose visually and saddles a form control with bookmarking and middle-clicking, features whose behavior on "cancel" is not merely useless but wrong. Middle-click Cancel and you get a new tab containing... what, exactly?

Everything a button lacks is not a gap. The missing middle-click, the missing copy-URL, the missing bookmark, the context menu with nothing in it — those absences were designed. They are the button's half of a contract with the user: this action belongs to this moment, in this context, and cannot be lifted out of it. The browser is not failing to give buttons link features. It is keeping a promise.

Use a link when the user may re-contextualize the action. Otherwise, a button.

Not "does it navigate." Not "does it write to the database." Whether the action survives being copied.

Which reframes the entire exercise. You are not picking an element from a list of two; you are deciding whether to hand the user a copy of the action's address. Sometimes that generosity is exactly right — articles, pagination, downloads, a filter state worth sharing. Sometimes it is a category error, and the honest move is to nail the action down where it lives.

Which is why the Triptych folks want Button Actions in HTML: <button action="/comments/123" method="GET">Cancel</button>. Right now a plain HTML author who wants fixed-context navigation has no primitive for it at all, so they reach for an anchor and lie, or reach for JavaScript and rebuild the browser badly. Two attributes, and the honest option becomes the easy one.

Stop asking whether the click changes the page. Ask whether the user gets to take it with them.
