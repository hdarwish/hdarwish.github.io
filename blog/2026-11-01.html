Your CPU is waiting, not working

We obsess over clock speeds and core counts, but the real performance killer is the silent tax of memory latency.

performancecachingdatabase

A CPU at 100% utilization is not necessarily doing 100% of the work you think it is.

The distinctionThe difference between a CPU that is busy and a CPU that is stalled.

01

The 100% Lie

You can write the most efficient algorithm in the world, but if your data lives in the wrong place, your system is still slow—and that's not a bug, it's physics. We like to act as though CPUs run code linearly for simplicity's sake, but in truth CPUs are incredibly complex beasts; they can potentially do many instructions at once, or sometimes none at all (despite our console showing 100%). A CPU is considered "idle" only if no task needs CPU time; this does not mean the CPU itself is being fully saturated.

So why would a CPU not be fully utilized, even if it appears to be at 100%? The answer is usually memory. Memory accesses are orders of magnitude slower than internal CPU operations. To give a good picture of how much so, a modern CPU might be able to process somewhere in the realm of 4-8 instructions per nanosecond. A memory access to RAM can take somewhere in the realm of 50-100ns. That means a modern CPU can do around 400-800 instructions for every one memory access from RAM.

02

The Cache Hierarchy

Given this, CPUs are built from the ground up to work their way around this. The most obvious way this is dealt with is CPU caches. CPU caches keep memory closer to the CPU than RAM, literally baked into the CPU chip. The closest cache (the L1 cache) takes around 1ns per memory operation- that's 50-100x faster than RAM! The "problem" here of course is that the CPU caches are fairly small; the L1 cache for a modern CPU is probably around ~64KB, while the farther caches max out at a few hundred MB for top end processors.

03

The GROUP BY Trap

A good database tries manipulating data in small "chunks" to take full advantage of caches, and you'll often hear cache utilization as being one of the top concerns of performance engineering. Let's look at GROUP BY aggregations to get a better grip on cache utilization. In GROUP BY, we're looking to take a dataset, group it by a certain column (or more), and perform certain aggregations. The "naive" method might be to open a HashTable keyed by the group key that grows ever larger. For every new row, you would check if that key exists- if it does, go to it's corresponding aggregation and update the result. Simple, right?

The problem is that if you have millions of unique groups, you're not utilizing your cache at all! Nearly every HashTable access will be a "cold" hit that goes to RAM. This means that although your CPU may /look/ like it's 100% utilized, in truth it'll constantly be waiting for cold memory accesses.

04

The Proof

To demonstrate this, we'll take our state-of-the-art Pivot engine and ravage it! We'll remove all our complex logic and replace it with simplicity. We'll then run a simple query SELECT count(*), UserID FROM hits GROUP BY UserID on the "hits" dataset ClickBench provides (99m rows). This query will give us a count per UserID, meaning we'll have an entry in our HashMap per UserID - I'll give you a spoiler here that there are ~17m unique UserID.

Our performance checks will be on a bare metal server from our good friends over at CherryServers (AMD EPYC 9124 Genoa, 16 cores, 128 GB DDR5). We'll confine ourselves to a single core, since this naive group by can't run on many cores. This takes... a whopping 3.9 seconds. Is that good? Is that bad? Everything in this world is relative, or so they say. If we run the query again (without restarting the server), it takes 3.6s. The second run is the one we're more interested in- there's no disk involved as everything is already sitting in our page-cache.

We'll measure two metric groups- percentage of CPU slots stalling because of memory (and not doing anything in the meanwhile), and percentage of CPU slots actually retiring a micro-op. And we get back this: 8364109137 ex_no_retire.load_not_complete # 50.1 % backend_bound_memory.

The turn

The CPU was at 100% utilization for 3.6 seconds. But 50.1% of those CPU slots were stalled, waiting for memory. The CPU wasn't working. It was waiting. And you couldn't tell from the top command.

Analogy A chef who can chop 100 onions per minute, but spends 99% of that time walking back to the warehouse to get another onion.

Where it breaks The chef is still technically 'working' the whole time, but the work isn't proportional to the output.

If you're deciding
When
When your CPU is at 100% but performance is poor
Prefer
Check for memory stalls using perf stat and look at backend_bound_memory
Avoid
Assuming high CPU usage means high throughput

Your cache is lying to you, and that's the point.
