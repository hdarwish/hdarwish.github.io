Your LLM gateway is a master key. Someone just stole it.

Here's a strange thing: a Python package whose entire job is to hold API keys for every LLM provider on Earth just shipped a version that hands those keys to an attacker. Not by breaking encryption. Not by finding a vault. By being installed.

A choke point with teeth

LiteLLM is the kind of tool that quietly becomes load-bearing. It sits in front of OpenAI, Anthropic, Gemini, and a hundred other providers, routing calls and — critically — holding the credentials for every one of them. Developers hand it their keys because that's the point of the thing. It's a single choke point for the entire AI stack. And a master key is only interesting if someone can get to it.

Now picture the attacker's shopping list. They don't need to break into your cloud account. They don't need to phish a developer. They just need to get a few lines into a package that thousands of teams install with pip install litellm. That's the whole attack surface. And on October 21st, 2026, someone did exactly that — with a stolen token and a single line of TOML.

The anatomy of a quiet implant

Version 1.107.0 on PyPI was not what the GitHub source had. The upstream repository was clean; the wheels were not. All seven wheels — Linux, macOS, Windows — carried three extra files in site-packages. The malicious release was up for hours: PyPI removed it by 13:23 UTC, and Docker images on Docker Hub and GHCR carried it between 11:46 and 14:20 UTC. That's roughly three hours of exposure, which in supply-chain time is an eternity.

Here's how it got in. The pyproject.toml in the source distribution had one extra line in the maturin build section: data = "cook". That single line told the build tool to copy a cook/ folder into the wheel. The sdist itself didn't include the folder, so the only visible change was that line. No public commit in the LiteLLM repo contained it. The attacker had the GitHub CLI credentials of three developers, believed to be harvested from the logs of an exposed internal deployment. With an organization owner's token, they pointed the release workflow at a lookalike repository and let the build system do the rest.

So the mechanism is not complex. It's a classic poisoned build, executed through a stolen token and a single TOML line. The real sophistication is in what the payload does once installed.

Two files, one master key

Python has a feature that makes this attack almost too easy: every process that starts on a host runs sitecustomize.py automatically, whether or not it ever imports the malicious package. Combined with cook.pth importing cook.py, the implant executes on every Python startup. No import of litellm required. Your cron job, your CI runner, your web server — all of them run the payload. Think of it as a parasite that doesn't need its host to take a bite; it just needs the host to breathe.

The first payload, cook.py, is a credential stealer. It collects SSH keys, cloud credentials, CI/CD secrets, AI tool tokens, browser passwords, and — the crown jewel — the LLM provider keys stored in the LiteLLM proxy database. It encrypts everything and exfiltrates it to www.litellm[.]dev. The second, sitecustomize.py, starts a background daemon that every hour reads a server address from a GitHub file, runs the stealer again, and downloads and runs whatever code that server provides. That's not a one-time theft; that's a persistent backdoor with a remote control channel.

The engineering consequence lands like a dropped wrench: your dependency graph is a security boundary, and this package just made it infinitely porous. The keys you gave LiteLLM weren't just exposed to the library's authors; they were exposed to anyone who could get the library to run code in your process. Which, as we've just seen, is anyone who can slip a line into a build.

The backdoor was already open

Here's the thing that makes this more than another supply-chain scare.

LiteLLM is not an ordinary dependency. It's a credential repository that you install into your environment. Every API key for every provider, sitting in a proxy database, waiting to be read. The backdoor didn't need to break encryption or find a vault — it just waited for the app to call the LLM and exfiltrated the key the developer already handed the library.

A dependency compromise is only as interesting as the keys it reaches.

And here's where the turn bites: you have probably built this machine yourself. Not the package — the concentration. Every time you centralize credentials in one tool, you've built a master key and handed it to the supply chain. The attack on LiteLLM is just the loudest version of a quiet pattern: the more convenient the hub, the more damage one compromised line can do. The weight of your entire AI stack now rests on a single TOML line.

What this frees you to do

You can't prevent every compromised package. But you can stop treating your LLM gateway as a trusted vault. The moment you install a package that holds keys for every provider, you've created a master key — and you've handed it to anyone who can get code into your environment. The fix isn't to stop using LiteLLM; it's to stop concentrating all your credentials in one place. Rotate keys on a schedule. Store them in a dedicated secrets manager, not in a proxy database. Treat every dependency as a potential exfiltration point, and assume that the package you install today might be malicious tomorrow.

This isn't paranoia; it's the cost of building on top of an ecosystem where a single TOML line can turn a trusted tool into a backdoor. The next time you run pip install, remember: you're not just installing code. You're handing out keys.

And the master key doesn't even need to break the lock — it just needs to wait for you to use it.
