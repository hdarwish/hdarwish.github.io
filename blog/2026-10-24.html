Your distributed database is a liar. Choose which lies.

September 2014. A weekend. Philip O'Toole puts SQLite behind a Raft log, pushes it to GitHub, and for years, nobody else bothers. Today, a dozen projects, some venture-funded, two acquired. So what was the actual struggle? Not the consensus. Not the Raft. The scariest bugs were in the ordinary SQL—queries that quietly assumed only one writer exists.

This is the story of twelve years of distributed SQLite, and it's not the story you've heard. The story you've heard is about consensus protocols and quorums and leader election. The real story is about a single-machine assumption so deep in SQL's bones that we stopped seeing it.

Consensus was never the bottleneck

Raft is a solved problem. You take a log, you replicate it, a majority acknowledges, a partitioned minority refuses writes. That's the CP design rqlite chose in 2014 and never changed. It's the same library InfluxDB and etcd used. The consensus part? Done. Replaced once (from goraft to Hashicorp's Raft in early 2016), but the design decision that mattered most was made in week one.

Every other feature—the HTTP API, the read-consistency levels, the snapshotting—followed from that one choice. It was the easy part. Here's the tell: when Litestream came along in 2021, it didn't bother with consensus at all. It just watched the WAL and streamed it to S3. No Raft, no quorum, no leader. And it was right. For most applications, you don't need a cluster; you need disaster recovery. Consensus is so easy that you can skip it entirely.

SQL's single-writer fantasy

Now the hard part. SQLite is a library. It runs inside your process. It assumes it is the only thing touching the database file. It assumes there is exactly one writer, and that writer is you, and you are not confused about that.

Picture a query like INSERT INTO t VALUES (1). On a single node, fine. Now replicate that write to three nodes via Raft. The leader applies it, the followers apply it. All good. But what about a query that reads the current value, increments it, and writes it back? On a single node, that's a transaction. In a replicated system, that read-modify-write has to go through the leader, and the leader has to serialize it with every other write. That's a throughput bottleneck, sure, but it's also a semantic one. What does SELECT COUNT(*) mean when the answer changes between nodes?

SQL doesn't have a concept of "leader". It has BEGIN and COMMIT. It has isolation levels. It has the implicit assumption that there is one source of truth, and it's the file on disk in front of you. Every distributed database that speaks SQL has to decide what to do with that assumption. dqlite embedded the database in a C library; Turso forked SQLite itself to change the engine. cr-sqlite went AP, letting multiple writers diverge and merge with CRDTs. Each one is a different answer to the same question: how many SQL promises are you willing to break?

The replication is not the point

Here's the realization that hits you halfway through the decade: you are not maintaining a replicated database. You are maintaining a carefully curated list of SQL promises you had to break.

You break BEGIN IMMEDIATE because there's no global lock. You break PRAGMA foreign_keys because the constraint check happens on the leader, and the follower doesn't know. You break last_insert_rowid() because it's per-connection, and your connections are now across a network. Each break is small, but each one is a footgun. The user writes a query that works perfectly on their laptop, and it silently does the wrong thing on the cluster. That's the real cost of distributed SQLite: not the consensus, not the replication, but the quiet un-keeping of promises.

The metric that matters isn't p99 write latency. It's the number of SQL features you can keep intact. rqlite's answer was to be conservative: only the leader writes, read-consistency levels give you a choice between strong and eventual. Litestream's answer was to avoid the problem entirely: no cluster, just a WAL stream to S3. The consequence for you, the engineer: before you reach for a distributed database, ask what SQL promises you're willing to break. Because you will break them.

The gift: a better question

So what do you do with this? You stop asking "which distributed SQLite should I use?" and start asking "which SQL promises can I live without?" The answer usually is: most of them, if you structure your writes right. If you append-only, if you avoid cross-row transactions, if you treat the database as a log with a cache on top—you can get away with a lot.

Litestream proved that most applications don't need a cluster at all. They need a recovery story. rqlite proved that if you do need a cluster, the consensus is the easy part, and the SQL compatibility is the tax you pay. Turso proved you can fork the engine to change the tax. cr-sqlite proved you can go AP and let the tax be eventual consistency.

The final lesson is this: a distributed database is not a database that runs on many machines. It is a database that has learned to lie about what it is. The best you can do is choose which lies you tell.

Twelve years in, the scariest bugs were never in Raft. They were in the queries we thought we understood.
