Your map is not a product. It is a file.

For a decade, we treated map tiles like a utility service. Protomaps and PMTiles just turned that utility into a commodity you can hold in your hand.

mapsinfrastructureself-hostingprotomapspmtiles

The barrier to self-hosting maps was never technical complexity or compute cost. It was the psychological weight of 'official' vendor lock-in and the friction of the deployment pipeline.

The distinctionThe difference between a map as a *service* (API, metering, black-box) and a map as an *artifact* (single file, HTTP Range requests, portable).

01

The $5 per 1,000 Trap

For most non-commercial projects, commercial APIs become prohibitively expensive the moment you go viral. Mapbox, for instance, charges $5 per 1,000 map loads once you’ve exhausted the free tier. This isn't just a price tag; it's a structural dependency. You are renting reality. Every zoom, every pan, every user who gets lost in your app is a line item on a bill that scales with your success. The psychological weight of this is heavy: it implies that your project's viability is tethered to a third party's pricing model.

But the real barrier wasn't the price. It was the *process*. To self-host maps, you traditionally needed a complex vector tile pipeline, a PostGIS database, and a tile server like Mapnik or CartoCSS. It was a multi-week engineering project. It was 'strategic infrastructure.' It felt like building a power plant to light a lamp.

02

The File That Is the Map

PMTiles, part of the Protomaps ecosystem, changes the ontology. It is a tile format that ships in a single file, accessible via HTTP Range requests. This is the mechanism that breaks the lock. Because it relies on Range requests, it does not need a specialized tile server. It does not need a database. It needs a file server. In fact, it needs a storage bucket.

The metric here is portability. The entire world map, at high resolution, is a 139GB file. You can download it from the Protomaps build page. You can upload it to Bunny.net, Cloudflare, or S3. That is the entire deployment. No Docker containers. No config files for rendering engines. No 'under the hood' complexity to debug when a tile 404s at zoom level 12. It is a file. You can copy it. You can version it. You can send it over USB.

03

The Economics of 'Good Enough'

Let’s look at the numbers from the source. Storing the 139GB world map on Bunny.net with 5x replication costs about $5/month. When a user loads a map of Europe and zooms into a city, about 5MB of data is transmitted. At $0.01/GB for bandwidth, that costs $0.00005. Compare that to Mapbox’s $0.05 per 1,000 loads (or $0.00005 per load if we normalize the flat fee, but often higher in practice with overages). More importantly, it is decoupled from the *user*. It is coupled to the *bytes*.

This is the consequence: 'Good enough' infrastructure is now a commodity. The Protomaps daily build is not 'inferior' to Mapbox. For 95% of applications—travel planning, logistics, local discovery, creative projects—it is structurally superior because it is under your control. You are not betting on a vendor's uptime or their willingness to keep your free tier generous. You are betting on HTTP and a file.

The turn

The 'official' vendor lock-in was a social contract, not a technical one. We accepted the black box because the alternative felt like *too much work*. PMTiles removes the work. It doesn't just lower the cost; it removes the *category* of 'strategic asset.' A map is no longer a service you subscribe to. It is a file you own. The moment you realize you can just curl the whole world, the fear of the map API evaporates.

Analogy Think of map tiles like coffee. For decades, if you wanted high-quality coffee, you had to subscribe to a delivery service that charged you per cup and controlled the roast. Now, you can buy a bag of beans (the PMTiles file), grind them yourself (the client-side rendering), and brew them in your own kitchen (your CDN). The quality is there, but the *dependency* is gone.

Where it breaks The analogy breaks when you need real-time traffic data or hyper-local, constantly updated POIs that the daily build doesn't capture. The 'bag of beans' is static; the subscription service is a live stream. For static or slowly changing geographic data, the bag wins.

If you're deciding
When
You are building a non-commercial or early-stage commercial app that uses maps, and you are wary of per-user API costs.
Prefer
Download the daily Protomaps build. Upload the .pmtiles file to a CDN that supports HTTP Range requests (like Bunny.net or Cloudflare with an edge function). Embed via MapLibre GL with the pmtiles npm package.
Avoid
Building a custom vector tile pipeline from OSM raw data. It is no longer necessary. It is a legacy pattern for a pre-commodity era.

The world is not a black box. It is a file. And you are allowed to hold it.
