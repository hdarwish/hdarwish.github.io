DuckDB's async I/O isn't an I/O feature. It's a scheduler rewrite.

For most of its life, DuckDB got away with the most old-fashioned data access path imaginable: a worker thread asks for bytes and then sits there, blocked, until the bytes arrive. Not because nobody noticed. Because it genuinely didn't matter. Filter and projection pushdown meant the engine barely read anything — prune the row groups, skip the columns, and the query touches a sliver of the file — and a local SSD forgave whatever was left. The bottleneck lived somewhere respectable: joins, aggregations, subqueries.

Then the same engine got pointed at S3.

Here is the part that should make you slightly uncomfortable. Nobody had written down the assumption "storage is close." It wasn't in a design doc as a constraint to be revisited someday. It was implied — baked into the shape of the execution model, where a task that needs data simply takes the thread it's running on and stops. That's a perfectly reasonable thing to do when a read costs microseconds. It becomes a catastrophe when a read costs an HTTP round trip, because now your worker threads, one per CPU, spend most of their lives holding a socket and thinking about nothing.

And you cannot patch that locally. That's the whole story.

Take the query from DuckDB's own write-up: FROM read_parquet('s3://bucket/file.parquet'), and for simplicity assume a single thread. A Parquet scan gets partitioned into row-group-based jobs, and each job contains one or more fetch tasks that issue byte-range requests. Synchronously, the sequence is: issue request, block, receive bytes, decode, aggregate, repeat. The thread is a single-track railway, and everything downstream waits on the slowest segment. On a remote object store, the slowest segment is not close.

The arithmetic here is brutal and it has nothing to do with code quality. The number of requests you can have in flight is what determines the throughput you extract from a high-latency store — throughput is in-flight requests divided by latency, and latency is a property of the internet, not of your engine. A thread that issues one request and then blocks keeps exactly one request in flight. So your ceiling on outstanding reads is your worker count, which is your CPU count, which was never chosen to be a concurrency budget for the network. It was chosen to be a parallelism budget for arithmetic. Two completely different jobs, accidentally sharing one number.

The naive fix — "use a non-blocking read call" — sounds like it solves this, and it doesn't, because the interesting question is not how do I issue a request without blocking. It's what does the thread do next. A syscall that returns immediately hands you a hot potato: a thread with no work and an obligation to eventually collect a result. Something has to own that potato. Something has to decide, at the scheduler level, who runs while the network is thinking.

DuckDB's answer is two thread pools. The REGULAR pool holds the worker threads — one per available CPU thread by default — and these do the real work: decoding, joins, aggregations. They prioritise regular work but will pick up I/O tasks when idle. The ASYNC pool exists for the blocking stuff, primarily remote reads. And the sizing is the tell: the default is 4× system threads, capped at 256.

Sit with that number. You are deliberately oversubscribing threads fourfold, which is precisely the thing every performance guide tells you never to do — and it's correct here, because these threads have almost no CPU utilisation. They exist to be blocked. A thread waiting on an HTTP response isn't competing for the CPU; it's competing for nothing at all. Concurrency and parallelism are different currencies, and DuckDB is buying the first with something that merely looks like the second.

Two pools alone still leaves latency on the floor, though, because if you only issue a read when a worker asks for it, the worker still waits — you've moved the wait, not removed it. So DuckDB schedules ahead: a read-ahead queue that issues fetch tasks for work further along than what the regular workers currently need. The stated goal is to keep as many ASYNC threads busy as possible. Speculation, promoted to a scheduling policy.

Which immediately creates a new problem, and I love that the design says it out loud: read-ahead buys throughput by holding memory. Prefetch faster than you decode and the buffers pile up until you fall over. So there's asynchronous memory governance sitting on top of the queue, throttling the prefetcher when it gets greedy. You did not receive a free optimisation. You received a control system — with a feedback loop, a tuning surface, and its own characteristic failure mode — where previously you had a blocking call.

The clearest sign of what actually changed is one sentence buried in the design: during the initial warm-up, the scan task parks, leaving the worker thread free to run other pipeline tasks. Not "the scan waits efficiently." The scan stops being a thing that occupies a thread. It becomes a thing that can suspend itself mid-flight, hand its worker back to the query to go do something unrelated, and be resumed later when its bytes have landed.

Async I/O is a scheduler change wearing an I/O change as a costume.

Everything else in that design is downstream of that one reclassification — the two pools, the read-ahead queue, the memory governor, the parking. Nobody made an I/O call faster. They changed what a task is permitted to be.

A synchronous scan is a chef who puts a pot on to boil and then stands there watching it, which was entirely rational in the original kitchen where the water boiled in two seconds. Move that kitchen into a building where water takes four minutes, and the fix isn't a faster kettle — it's a chef who can walk away and be called back. Notice where the analogy breaks, because it breaks somewhere expensive: the chef remembers what she was doing. A parked task has to have its resumption state made explicit — where in the row group it was, which buffers it owns, what it's waiting on — and that explicitness is the engineering cost of the whole feature. The thread's stack was doing that bookkeeping for free, invisibly, by accident of how function calls work. The price of async is doing it by hand.

So here's the portable thing, and it has nothing to do with Parquet. Every system you have built encodes assumptions about latency that were never stated as assumptions, because at the time they were simply true. Storage is close. The network is reliable. The call returns fast enough that blocking is free. These aren't bugs. They're good engineering decisions that got compiled into a concurrency model and then quietly lost their comments.

When you move a system into a new environment and it goes mysteriously slow, resist the urge to hunt for the slow function. Ask instead which unwritten latency assumption just got violated — and then ask the harder question, the one that actually pays: what does my scheduler believe about waiting? Usually the thing that has to change is not the call that got slower.

It's what your system thinks a thread is for.
