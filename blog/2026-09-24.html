Your remote editor is a remote-access tool in disguise

Open VSCode, connect to a server, and you have just installed a full Node.js binary on that machine. You didn't click anything. You didn't approve anything. You just wanted to edit a file.

Millions of developers do this every day, and the tool is so smooth that nobody looks under the hood. The engineers at Fly.io finally did — because they wanted to plug their own platform into the same flow — and what they found reads like a nature documentary with a body count.

The Way We Thought It Worked

Emacs has been doing remote editing forever with a tool called Tramp. The design philosophy is elegant: it lives off the land on the remote connection, running Bourne shell commands over your SSH session to extend your editor into that environment. Lightweight, clever, entirely within the spirit of SSH itself.

You'd think VSCode would take Tramp as a starting point, simplify it, swap the Elisp for TypeScript.

You'd think wrong.

The Full-Scale Invasion

VSCode doesn't send a few commands. It mounts an invasion. When you connect, it runs a Bash snippet stager that downloads an entire agent — including a binary installation of Node.js — onto your remote machine. This is not a light-touch protocol.

This is a full deployment.

The agent opens a WebSockets connection back to your running VSCode front-end. Through that connection it can do absolutely everything: wander the filesystem, edit arbitrary files, launch its own shell PTY processes, and persist itself — it doesn't clean up after itself.

In security circles, there's a name for tools that work this way. It's the same name as a small rodent. You don't need a lab coat to see the resemblance.

What This Means For You

Say you're using VSCode to remote-edit something on a dev server. Right now, on that server, a full Node.js process is running that can do anything your user can do. It can modify files. It can run processes. It persists. This is the price of smooth remote editing.

On a dev server, maybe that's acceptable. Point it at production during an incident and the word apoplectic starts to feel personal.

The Trap

Every piece of this system makes sense in isolation. The stager bootstraps, so it downloads Node. The agent needs to communicate, so it opens WebSockets. The connection needs to edit files, so it gets full filesystem access. Each step is a reasonable engineering decision.

But together they form a Rube Goldberg machine — an absurd chain where the ball rolls down a ramp, hits a lever, drops a weight, and finally types a character into a file.

You are not running a text editor. You are running a remote-access tool dressed as one.

The smoothness is the trap.

What To Do With This

The Rube Goldberg comparison breaks in one important place: a Rube Goldberg machine is built to be watched. This one is built to be invisible. The whole point is that you never see the ball rolling or hear the lever click — you just type, and the character appears.

So you don't abandon VSCode. You stop treating it like a fancy text editor and start treating it like what it is: a deployment you never signed for. Before you point remote development at something important, ask whether it's a clean-slate instance, and whether the blast radius is one you can live with.

The convenience is real. So is the invasion. The only way to keep the machine from working against you is to know exactly what it's doing when it works for you.
