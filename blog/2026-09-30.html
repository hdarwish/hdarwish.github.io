SIMD is the last free lunch in computing

You've probably seen the loop a hundred times: for (byte in bytes) or for (value in array). It's so unremarkable you'd never think twice. But here's the strange truth: that loop, sitting in your code right now, is leaving a 2x, 8x, even 16x speedup on the table — and the fix is not a new algorithm, not a better data structure, not a rewrite in Rust. It's a CPU feature that's been in your machine for twenty years, and most engineers have never once used it on purpose.

SIMD has a reputation problem. It's seen as the dark arts of game developers and HPC wizards, something too complex for everyday programming. That's wrong, and it costs us dearly. Every time you write a naive loop over a hot array, you're paying full price for something the hardware will do for a fraction of the cost — if you'd only ask.

The last free lunch

Here's what SIMD actually is: a CPU's ability to operate on multiple values with a single instruction. Instead of comparing one byte at a time, the CPU compares 4, 8, or even 16 bytes at once. That's it. That's the whole trick. The speedup is direct: process 8 bytes per instruction instead of 1, and the loop gets up to 8x faster (minus overhead).

And it's not a niche trick. As Mitchell Hashimoto puts it in his July 2026 post, Everyone Should Know SIMD, the common case — "process N values at a time" — follows a simple, repeatable shape. Once you learn it, writing SIMD is "just about as easy as a for loop." The hard stuff, like simdjson's insanely optimized parsing, is a whole other level. You don't need that. You need the loop that runs a million times a second.

Think of it like this: your CPU is a cashier who can only handle one customer at a time. SIMD is handing them eight customers at once. The cashier's job doesn't change — they still process each customer — but the line moves eight times faster. The analogy breaks, of course, because the cashier doesn't actually do eight things at once; they're just really good at batching. But the point stands: the work is the same, the throughput multiplies.

The common shape

So how do you actually write it? Hashimoto breaks it down into five steps, and once you see it, you'll never unsee it:

  1. Broadcast any constants you need into a vector (e.g., @splat(0xF)).
  2. Loop over the input one vector-width chunk at a time — 4, 8, or 16 values per iteration.
  3. Perform the comparison or arithmetic across all lanes in parallel.
  4. Reduce the vector result to a scalar (e.g., @reduce(.And, ...)).
  5. Handle the remaining elements with a scalar tail — your old loop, just for the leftovers.

That's the entire pattern. Let's make it concrete. Hashimoto's example comes from Ghostty, his terminal emulator: a slice of decoded codepoints, and you want to find the end of the next run of printable characters (those above 0xF). The scalar loop is one line:

while (end < cps.len and cps[end] > 0xF) end += 1;

Simple. Clear. And slow. Here's the SIMD version, stripped of comments:

if (simd.lanes(u32)) |lanes| {
    const V = @Vector(lanes, u32);
    const threshold: V = @splat(0xF);
    while (end + lanes <= cps.len) : (end += lanes) {
        const values: V = cps[end..][0..lanes].*;
        const greater_than_threshold = values > threshold;
        if (@reduce(.And, greater_than_threshold)) continue;
        const mask: std.meta.Int(.unsigned, lanes) = @bitCast(greater_than_threshold);
        end += @ctz(~mask);
        break;
    }
}
while (end < cps.len and cps[end] > 0xF) end += 1;

Twelve lines instead of one. But look at the payoff: up to 4x on ARM NEON (Apple Silicon), 8x on AVX2 (most modern x86), 16x on AVX-512 (some Intel and AMD Zen 4+). In Ghostty's real-world end-to-end throughput on an AVX2 desktop, that translated to about a 5x speedup — not the theoretical 8x, because the SIMD loop isn't the whole pipeline, but 5x is still 5x. From a one-line loop.

Here's the mechanism-to-metric-to-consequence chain: the comparison values > threshold runs across all lanes in parallel, so one instruction does the work of eight. The metric is throughput: instructions per element drop from ~1 to ~0.125. The consequence? A terminal that feels faster because it's not spending cycles it doesn't need to.

Why can't the compiler do this?

You might be thinking: "Why doesn't my compiler just auto-vectorize this?" Good question. The answer is that compilers are getting better, but they're conservative. They have to be. Auto-vectorization fails when the compiler can't prove the loop is safe to parallelize — aliasing, data dependencies, variable trip counts. And even when it does vectorize, it often does so with a generic width that leaves performance on the table. The human who knows the data is 16-byte aligned can hand the compiler a 16-wide vector and watch it fly.

But here's the thing: you don't need to hand-write SIMD for every loop. The cost-benefit is clear. If the loop processes only a handful of bytes, skip it. But if you're iterating over hundreds, thousands, millions of bytes — JSON parsing, string scanning, array transformations, image processing, network packet inspection — the payoff is huge. And the cost is learning a five-step pattern that takes an afternoon.

Every engineer reading this has already left SIMD performance on the table.

Let that sit for a second. The loop you wrote last week, the one that runs on every keystroke or every request — it could be 5x faster, and you didn't even know the option existed. That's not a criticism. That's the tragedy of a missed opportunity.

The gift

So what do you do with this? Start small. Pick a hot loop in your codebase — the one you've profiled, the one that shows up in the flame graph. Rewrite it using the five-step shape. You'll need a SIMD library for your language (Zig has @Vector, Rust has std::simd, C++ has intrinsics, Go and Python are harder — but you can drop to C or use assembly). The point is not to vectorize everything; it's to know when it's worth it.

The rule of thumb: if the loop moves bytes, SIMD probably helps. If it moves a few dozen bytes, don't bother. If it moves millions, you're leaving money on the table.

And when you do write it, remember the scalar tail. That's the part that catches the leftovers, the elements that don't fit neatly into a vector. It's your old loop, one more time. It's the safety net that makes the whole thing work.

SIMD is the last free lunch in computing. Moore's law gave us more cores, but we can't always use them. SIMD is already there, in every CPU, waiting for you to ask. The next time you write a for loop, ask yourself: is this the best the hardware can do? The answer, almost certainly, is no.

Go get your 5x.
