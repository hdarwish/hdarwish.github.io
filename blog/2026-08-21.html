Rust checks your program. Nobody checks your build.

On August 20, 2026, someone pushed arrayref 0.3.10 to crates.io. The crate does one boring, beloved thing — it hands you references to fixed-size array slices — and it is buried somewhere in an enormous number of dependency trees. The new version added exactly one thing: a dependency on a crate called proc-macro1. Not proc-macro2, the real one that every macro author in the ecosystem depends on. proc-macro1. Published by dtolney, which is not dtolnay, with a Cargo.toml that forged authors = ["David Tolnay <…>"] and pointed repository at a dtolnay/proc-macro1 URL that 404s.

Its src/ directory was a genuine, working copy of proc-macro2. So your build succeeded. Your tests passed. Your binary was fine.

The malware was in build.rs, and it ran while rustc was still working.

Rust's entire safety proposition is enforced at compile time. Borrow checking, lifetimes, aliasing rules, the whole magnificent apparatus — it all happens before your program exists. That is precisely the window in which this payload executed. On your machine. As your user. With your SSH agent, your cloud credentials, your registry tokens, your ~/.cargo, all sitting right there. The compiler was busy proving that your code couldn't have a use-after-free while a detached process it had just spawned phoned home to an IP address in Kansas.

Notice that nobody had to make a typo. The typosquat wasn't aimed at your fingers; it was aimed at a Cargo.toml deep in your tree that you have never opened. A caret requirement like arrayref = "0.3" — which is what almost everyone writes, because that is what the tooling encourages — happily accepts 0.3.10 the moment it exists. One cargo update, one cold CI cache, one fresh clone, and a crate you have never heard of gets a shell on the machine. The lockfile is the only thing standing between you and that, and lockfiles are routinely regenerated by people trying to be tidy.

The gears themselves are worth examining, mostly for how ordinary they are.

The payload, quoted in RustSec advisory-db #3161, lives in proc-macro1-1.0.107/build.rs. It stores its server address as base64 fragments — "aHR0cHM6Ly8=", "MjMuMjU0Lg==", "MTY1Lg==" and so on — and reassembles them at build time. Decoded, they yield a payload host at 23.254.165.112:9089 and a command-and-control endpoint at 23.254.165.112:443. Split across five string literals, no host anywhere in the source, nothing a grep for a domain would catch. Then it fetches an architecture-specific binary over TLS — and here is my favorite grim detail — over a TLS connection configured to accept any certificate without validation. The malware author wanted encryption for opacity, not for trust. They were hiding from you, not verifying the server.

On Unix it writes and runs /tmp/rust-setup. The name is not an accident; it is the sort of thing you'd glance at in a process list and assume was toolchain business. On Windows it drops a PowerShell script plus a VBScript launcher into %TEMP%, starts them hidden, and then abandons the child process — so the compile finishes clean, the exit code is zero, and the malware outlives the build that created it.

The account behind arrayref, droundy, appears to have been compromised. The same account also pushed poisoned internment 0.8.7 and append-only-vec 0.1.9. Every associated GitHub repository — and the entire github.com/droundy account — now returns 404, so the upstream code you'd want to diff against has evaporated. crates.io has pulled the malicious versions, along with a cluster of supporting typosquats: proc-macro-en, aovine, arone, aronenao, tinymember.

Try this analogy on. Memory safety is an extraordinarily rigorous inspection of the car at the end of the assembly line: every weld measured, every bolt torqued, and the inspector genuinely will not let a bad unit through. This attack did not tamper with the car. It gave the night-shift cleaning contractor a key to the plant. The inspection was flawless and completely irrelevant, because the target was never the product. The analogy breaks in one place worth naming: a real factory intruder would eventually show up in the cars. This one has no reason to bother. The car is a distraction.

So ask what a build machine actually contains. Not a running service with a scoped IAM role and a read-only replica — that is what we spend our security budget hardening. A build machine holds the keys to make things: signing keys, publish tokens, container registry pushes, deploy credentials, the private repos of everything you own, and — increasingly — API keys for whatever model your coding agent talks to. Production is monitored, alarmed, and deliberately impoverished. CI is trusted, chatty, and rich. The payload's real target was never your users.

Memory safety protects your binary. Nothing protects the machine that builds it.

Because cargo build is not a compiler invocation. It is a remote code execution primitive that we have collectively agreed not to think about, and it always has been. build.rs is arbitrary code, compiled and executed before your crate is even looked at, unsandboxed, with your full ambient authority, from every transitive dependency you have never read. There is no permission model. There is no allow-network = false. A build script that links a C library and a build script that exfiltrates ~/.aws/credentials are, to Cargo, the same kind of event. And this is not a Rust failing — npm has postinstall, Python has setup.py, and Make has had this property since the 1970s. Rust is simply an unusually sharp place to see it, because Rust is the language that taught a generation to expect the compiler to have their back.

The gift here is a better question. Stop asking "are my dependencies safe?" — you cannot audit a dependency tree by reading it, and the attacker already knows that. Ask instead: what can the build steal? That question has answers you can act on this afternoon. Give CI credentials that expire in minutes, not hours. Deny build containers outbound network by default, so a reassembled base64 IP literal has nowhere to go. Pin and vendor, so a fresh 0.3.10 cannot appear underneath you overnight. Keep publish and signing tokens on a machine that never compiles third-party code. Notice that --offline is a security feature.

None of that requires guessing which crate is next. It only requires admitting that your compiler is a guest with root, and treating it accordingly.

Rust proved you can make the program trustworthy. The room it was written in is still wide open.
