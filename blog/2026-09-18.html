The Proof Passed. The Law Was Wrong.

A theorem can make one forbidden game state impossible while proving almost nothing about whether the game is correct.

Picture a generated board game with a law saying that no move may occur after victory. The implementation arrives with a valid proof: once the state is marked terminal, every attempted move is rejected. Splendid. Unfortunately, the code recognizes victory using the wrong pattern, so the terminal flag itself is nonsense. The theorem has guarded the drawbridge while somebody quietly moved the castle.

A proof answers exactly one question

Proof-checked AI code invites a dangerously comfortable sentence: the code is verified. Verified against what? If that question receives a vague answer, mathematical confidence starts laundering ordinary ambiguity into something much grander—and much harder to challenge.

In a Bend-style workflow, generated code is accompanied by proofs that its stated laws hold. A checker does not inspect the programmer’s intentions, infer the product requirements, or squint thoughtfully at the interface. It checks whether a formal proposition follows from specified assumptions under the system’s rules. That reduces one important metric—the number of implementations violating those propositions—but says nothing by itself about defects the propositions failed to name.

The checker is doing real work.

Suppose the game law is written schematically as terminal(s) → apply(s, move) = error. A proof may establish this for every representable state and move, not merely for the examples someone remembered to test. A test suite samples executions; the theorem covers the entire modeled state space. For this property, you no longer need to hope that testing happened to visit the embarrassing corner.

That guarantee is enormous—and exactly bounded.

The loopholes are inside the law

Now inspect the nouns. What makes a state terminal? Which states are representable? What counts as apply? If the definition of victory omits diagonal wins, the theorem remains valid. If malformed boards are excluded by an overly strong precondition, the theorem says nothing about them. If the model contains no time, storage failure, concurrency, or external service, no proof inside that model can constrain those absent things.

The modeled state space is not reality. It is a fenced garden cut from reality, and the proof tells you—with extraordinary precision—what can grow inside the fence. It cannot tell you whether the fence was put in the right place. This analogy breaks where all physical gardens do: formal boundaries can be perfectly exact, while wooden fences decidedly cannot. The useful point is omission, not carpentry.

Specification incompleteness has a particularly mischievous cousin: vacuity. A law of the form “for every valid request, property P holds” is effortless to prove if valid accidentally rejects every request. The implication is true because its premise never occurs. Proof success rises while useful behavioral coverage falls through the floor.

A green checker measures derivability, not relevance.

Think of a proof checker as an impossibly strict contract court. If the contract says the contractor must paint every listed door blue, the court can establish that every listed door is blue; it cannot object that the kitchen door was omitted from the list. The analogy breaks in the proof system’s favor: within a formal model, the guarantee can be absolute rather than dependent on testimony, evidence, or enforcement. Yet omission remains omission, even when certified with exquisite rigor.

Incorrect laws are worse than incomplete ones because they can make the wrong behavior mandatory. A mistaken invariant may forbid a legitimate state. A postcondition may encode the wrong rounding rule. A security policy may prove that only “authorized” callers gain access while defining authorization too broadly. Conformance improves while the product deteriorates—a nasty inversion that proof-pass rates will cheerfully report as progress.

AI can agree with itself perfectly

Generative systems add another gear. If the same model drafts the implementation, proposes the laws, and repairs the proof whenever checking fails, it can produce a beautifully coherent account of one misconception. The code and specification are no longer independent witnesses; they are two copies of the same story wearing different hats. Agreement looks impressive, but correlated agreement is weak evidence.

This is why tests still matter, although their job changes. Property-based tests can attack whether formal predicates match executable examples. Mutation testing can alter the implementation or specification and ask whether the surrounding laws notice. Counterexample search can expose states that satisfy the formal preconditions but violate an external oracle. These techniques test specification sensitivity: whether a plausible mistake is detected, not merely whether today’s proof term type-checks.

Once the checker has removed a large class of implementation slips, the failures left standing are omissions, mistranslated requirements, vacuous assumptions, and models that politely exclude reality’s untidy edges; the certificate is strongest exactly where the question has become weakest, because the remaining uncertainty sits in what humans or models chose to ask.

Proof-carrying AI code moves software risk from implementation into specification.

The proof did not remove uncertainty. It concentrated it.

Review the claim, not the certificate

The portable habit is to review every proof obligation adversarially. Ask what behavior would still be disastrously wrong while satisfying this law. Try weakening the precondition. Check whether the postcondition distinguishes every outcome users care about. Write a second formulation independently and see whether the two claims agree. Review effort should follow the risk, and the risk now lives in the sentence being proved.

This also changes what you should demand from tools such as Bend. A proof dashboard should not merely celebrate accepted theorems; it should expose assumptions, highlight unmentioned state, detect vacuous implications, generate counterexamples to nearby stronger claims, and show which requirement supplied each law. Proof latency matters for developer flow. Traceability and mutation sensitivity determine whether the proof deserves belief.

Machine-checked proof does not become smaller under this scrutiny. It becomes useful enough to treat seriously. Tests catch witnessed failures; types exclude broad families of nonsense; proofs rule out formally named behaviors. Each instrument is magnificent precisely where it reaches—and silent where it does not.

The machine can certify the law. You still have to hear what the law never said.
