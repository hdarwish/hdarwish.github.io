Your AI is a shared memory

The 'stateless' promise of serverless inference is a lie. The KV cache is a global variable, and most engineers are too lazy to isolate it.

AI SecurityInferenceKV CacheServerless

In traditional web servers, a request is a transaction. It arrives, it is processed, and the memory is wiped clean before the next request arrives. We built our entire mental model of 'serverless' on this assumption: no state, no side effects, pure functions.

The distinctionThe distinction between *logical* statelessness (the API contract) and *physical* statefulness (the hardware reality of the KV cache).

01

The Phantom Memory

Cloudflare just patched a vulnerability in their GLM-5.3 Workers AI model. One user's private prompt leaked into another user's response. Not because of a network bug. Not because of a database misconfiguration. Because the AI's 'memory' wasn't actually wiped between requests.

This is not a bug in the code. It is a bug in the architecture. When you run a Large Language Model, you are not running a stateless function. You are running a stateful machine that *pretends* to be stateless for the sake of your API contract.

02

The KV Cache is a Global Variable

To understand how this happens, you have to understand what the KV (Key-Value) cache actually is. In a Transformer model, generating each new token requires the model to 'remember' all previous tokens in the sequence. Storing these attention weights is expensive in computation. So, we cache them. This is the KV cache.

Here is the trap: The KV cache is often allocated in memory that is *reused* for performance. If you are serving multiple concurrent requests on the same GPU, the hardware scheduler might reuse memory blocks from a previous request if it hasn't been explicitly zeroed out or if the isolation boundary is flawed. The KV cache is effectively a shared mutable global variable that lives in VRAM.

03

Why Lazy Is Dangerous

Why do we get this wrong? Because the performance penalty of explicit memory isolation is real. Zeroing out the KV cache for every single request, or allocating strictly disjoint memory pools, adds latency. In the race to optimize for throughput and low p99 latency, engineers often rely on the *assumption* that the inference framework handles isolation. They trust the library. They trust the 'serverless' abstraction.

But abstraction is not a security boundary. It is a convenience layer. If the underlying inference engine (like SGLang or vLLM) manages memory pools, and if that pool management has a race condition or a default configuration that favors reuse over safety, your 'stateless' endpoint is actually a stateful leak.

The turn

You have built this machine. Probably several times. You have optimized your inference pipeline for speed, trusting that the 'serverless' label means your data is as ephemeral as a UDP packet. It isn't. The KV cache is a sticky note left on a shared whiteboard, and you just let someone else read it.

Analogy It's like a hotel that promises 'clean rooms' but only changes the sheets if the guest complains. The room (memory block) is the same, the furniture (weights) is the same, but the towels (KV cache) might still have the previous guest's soap residue on them.

Where it breaks The analogy breaks because in a hotel, the 'state' is physical and visible. In a KV cache, the state is numerical and invisible until it leaks into the output tokens.

If you're deciding
When
Deploying any LLM inference endpoint that uses a KV cache
Prefer
Explicitly verify memory isolation. Audit the inference framework's memory management. Assume the cache is shared until proven otherwise.
Avoid
Relying on the 'stateless' API contract as a security guarantee. Assume that because the API returns 200 OK, the memory was wiped.

Stop treating your inference engine like a pure function. It is a stateful machine with a short-term memory, and you are the only one who knows what it is remembering.
