The GPU driver is the one thing you were never allowed to link

A fully static musl binary cannot dlopen() the host's glibc-linked Vulkan driver. There is no dynamic section in the ELF, no interpreter, no ld.so sitting in the address space to ask. The one dependency the machine insists on providing is the one your beautiful single-file executable has no mouth with which to accept.

That sentence — narrow, unglamorous, entirely technical — is why an enormous amount of Linux software ships as a container, an AppImage, a Flatpak, or a 400MB tarball with somebody else's Ubuntu inside it.

Consider how much engineering lives downstream of it. Whole packaging ecosystems, image registries, layer caches, base-image CVE scanners, "works on my machine" arguments that end with shipping the machine. The standard explanation is that Linux dependency management is intrinsically hopeless, so the grown-up move is to surrender and bundle a userland. But look at which dependency is actually doing the forcing. It isn't libpng. It isn't the C++ runtime. It's the graphics driver — code that must match the kernel module and the silicon in front of it, code you cannot vendor even in principle, because you do not know what GPU the user bought.

SoLo, which hit the HN front page at 309 points, takes that observation and does something heretical with it: keep the static binary, and become the dynamic loader yourself.

The mechanism is more audacious than the README's calm tone suggests. SoLo exposes a dlfcn-shaped source API — your code calls something that looks like dlopen and dlsym — but behind that API sits its own ELF loader, for x86-64 and aarch64. It maps the host's shared object, walks its program headers, applies its relocations, and resolves its symbols. That is the easy half, and it is not easy. The hard half is that the object you just mapped was compiled and linked against glibc, so it does not merely want glibc functions; it wants glibc behavior. So SoLo carries a glibc ABI bridge built on top of musl.

Think about what such a bridge has to absorb. glibc versions its symbols, so a driver's imports may name GLIBC_2.17 or GLIBC_2.34 and expect the loader to pick the right one. glibc ships IFUNC relocations, where the "address" of memcpy is a resolver function that must be called at load time to choose a CPU-specific variant. Thread-local storage has its own relocation types and its own quiet assumptions about who allocates the block and where. Get any of that wrong and you don't get a clean error — you get a driver that runs for a while and then dies inside a lock.

The critical design choice is what SoLo refuses to do: it does not smuggle a second libc into the process. Two libcs in one address space is a haunted house — two heaps, so memory allocated by one is freed by the other; two views of errno; two opinions about who owns TLS. One libc wearing a convincing glibc mask is merely very difficult. Difficult is a thing engineering can finish.

An analogy, and I'll tell you where it breaks. A dynamic loader is a customs office. Normally the host country runs it: ld.so checks papers, stamps symbols, decides which library satisfies which import. A static binary is a country that abolished customs — nothing crosses, ever, which is wonderfully simple right up until you need something that only grows on the other side of the border. SoLo doesn't reopen the old office. It builds a small private one on its own soil, staffs it with its own inspectors, and issues a phrasebook — the ABI bridge — so glibc-speaking cargo can be understood by musl-speaking clerks. Where it breaks: real customs can refuse entry. SoLo's loader must satisfy every symbol the driver asks for, or the driver simply doesn't work. Less a border, more a promise to answer every question correctly.

Which invites the obvious objection: fine, it loads one hand-picked driver in a demo. Everyone's clever loader works on the library they tested it against.

So look at what's in CI. On every commit, SoLo loads the shared libraries of the 1,000 most-installed Debian packages — over 2,100 host objects — through its own loader, on both x86-64 and aarch64. That isn't a demo; it's a continuously re-tested empirical claim about how much glibc-ABI weirdness actually exists in the wild. The end-to-end proof is the honest kind too: a fully static executable enters a statically linked Khronos Vulkan loader, pulls in the host's unmodified ICD and its non-glibc dependencies through SoLo, builds a device, a storage buffer, a descriptor set and a compute pipeline, dispatches a checked-in SPIR-V shader, then maps the result and writes a PNG through statically linked libpng. AMD radv, radeonsi, Intel, NVIDIA — and an Apple M1 under Asahi. You can readelf -dW the released binary and find no dynamic section at all.

Which means this was never a rebellion against dynamic linking, and never a trick for sneaking static binaries past a limitation. It's a redrawing of a line that a tool drew for us decades ago and we never questioned. Exactly one category of code legitimately belongs to the host: the code that knows what hardware is physically present. Drivers. Your app, your renderer, your image codecs, your terminal emulator have no business being renegotiated at install time on a stranger's machine.

Static linking fails only where the host must own the code. So bridge — don't containerize.

If that's right, then containers-as-deployment were never solving a dependency problem. They were solving a boundary problem, and solving it by moving the boundary out so far that it swallowed an entire operating system. The real boundary was always thin. It was the driver. Everything else was collateral damage, dutifully packaged and shipped.

Here's the portable part. When a system forces you toward a heavyweight solution, go find which single dependency is actually applying the force. Usually there's one. Usually it's small. Usually it is genuinely irreducible for an excellent reason — and the right response is a precise bridge across that one gap, not a bulldozer that flattens the neighborhood until the gap is no longer visible from the road. Bundling is what you do when you've stopped asking where the line is.

The host keeps the hardware. You ship one boring file.
