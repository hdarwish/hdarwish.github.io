Your cache is the cheapest CSS you'll ever ship

There is a sentence that should get you laughed out of any performance review: "We made the site faster by shipping more CSS." It is a real sentence. It's the title of a GitHub engineering post. And it's true.

If you've spent any time in web performance, you know the religion: fewer bytes, fewer requests, less everything. Minify. Purge. Split. Inline the critical stuff. Get that stylesheet down to 3KB or you've failed the audit. This is a fine religion for one page.

The problem is that nobody visits one page.

The cost model you've been using is wrong

CSS has two entirely different costs, and we've been optimizing the wrong one. The first cost is transfer — the bytes that travel across the network. The second is work — parsing rules, building the cascade, applying styles. Transfer is paid over and over, every time the browser has to fetch. Work is paid once, and then it's done, because the browser keeps the result.

When you inline "critical CSS" into every page's HTML — the orthodox move — you save a request on the first paint. But you've also made a promise you can't keep: that this CSS will never be needed again on this site. It will. Every page has a header. Every page has a footer. Every page has buttons.

You've photocopied the same chapter into every book in the library.

Each of those photocopies gets re-fetched and re-parsed on every navigation. The bytes you saved on page one, you pay for on page two, three, and forty-seven — with interest, because you're also paying the round-trip latency to fetch them at all.

What the browser actually does with a cached file

A shared stylesheet is the opposite bet. You ship more CSS — the whole site's CSS, not the page's — and the first view pays for it. But here's the mechanism that makes the bet pay off: after that first fetch, the browser stops asking. The file is in the HTTP cache, and every subsequent page navigation reads it from disk, not from the network.

The metric that matters is not the size of your first load. It's your cache hit rate across a session — how many of the bytes the browser needs were already there when it needed them.

This is the part that feels like cheating, so let me say it plainly: a cached stylesheet costs the browser almost nothing to reuse. The expensive things are round trips. A 100KB cached file beats a 5KB uncached file on every page after the first — because the 5KB file still has to cross the network, and the 100KB file doesn't.

Picture a courier who charges per delivery, not per kilogram. You'd stop sending five small packages and start sending one big box, wouldn't you? That's the whole argument. The analogy breaks when the site is a single page with one view — then the big box is pure waste. But a site is rarely one view.

Ship more, so the browser fetches less

None of this means CSS size doesn't matter. It means CSS size matters less than CSS fetch-count. The engineering consequence is a real reordering of priorities:

  • Before splitting your stylesheet by route, ask whether the split creates a cache miss on navigation.
  • Before inlining critical CSS, ask what it costs every page after the first.
  • Before celebrating your 3KB first load, measure the second load. And the third.

The browser doesn't re-pay for work it has already done. The network re-pays you for every byte you make it carry twice.

The cheapest CSS is the CSS you never fetch twice.

You have probably built the photocopier. Most of us have. We split stylesheets by route, we inlined critical paths, we shaved kilobytes and added round trips — and we did it in the name of performance, because "ship less" is such a clean rule that we never noticed it was optimizing the wrong number.

The rule isn't "ship less." The rule is "make the browser do less." Sometimes those are the same thing. Often they are opposites.

So the question to carry into your next performance review isn't "how many bytes is this page?" It's "what does the browser have to do again?" Every byte it has to re-fetch is a byte you already paid for once. Every byte it can read from its own cache is a byte that's finally free.

Optimize the session, not the page. The page is just the first installment.
